# Personal Agent面试材料

## 可以先讲的结论

这是一个复用原版Pi Loop、由宿主管理长期状态与授权的单用户Agent。当前工程证据较扎实的是SQLite持久任务、Manual Goal单次授权与Checkpoint、交互Session恢复及受控Memory投影。它还不能被描述为经过长期生产验证的自主Agent：通知恢复有缺口，Goal故障分类存在当前分支缺陷，模型语义可靠性没有本轮真实评测，自动主题路由在被测分支不存在。

2026-11-07冻结`e2c95c0`对应生产源码，另建20场景离线评测：**16通过、3失败、1未实现跳过**；现有及新增自动测试**591/591通过**。费用0、正式数据访问0、真实飞书发送0。完整结果、Hash与轨迹见[评测结果](EVAL_RESULTS.md)。这些数字都不是线上成功率或模型Benchmark分数。

## 架构和完整执行链

入口分Console、飞书和本机Web。Channel先验证身份并创建Run，`AgentExecutor`是业务层唯一模型执行接口。交互Session复用原版Pi：模型看到白名单工具，决定是否提议工具调用；宿主`OperationGuard`再核对当前用户原话、目标、版本和显示/确认凭据。业务服务保存Task、Goal或Memory的事实。后台Scheduler/GoalRunner独立于终端循环，使用独立临时Pi Session执行，提交状态后再走统一Channel通知。

| 对象 | 保存什么 | 不替代什么 |
| --- | --- | --- |
| Task/Run | 一次性指令、UTC到期时间、绑定接收人、执行/投递结果 | 不用对话历史充当任务队列 |
| Goal/Plan/Step/Execution | 长目标、批准的版本计划、稳定步骤、单段执行及Checkpoint | 不以模型的“做完了”更新整个目标 |
| Pi Session | 原生JSONL对话上下文；后台临时会话不混入前台 | 不是长期知识库或任务事实源 |
| Memory | 明确授权保存的四类当前知识；Markdown事实源和独立索引 | 不自动把任务进度或闲聊推断保存成事实 |
| WorkThread | Web主题名称、归属、对象ID关联 | 不授予访问权，不负责执行或自动主题路由 |

Pi SDK负责模型协议、消息、工具调用循环及公开Session管理；宿主负责身份、授权、调度、预算、状态机、事务、恢复、投递和审计。没有Fork SDK，没有另写Agent Loop，没有直接改Pi内部消息数组。

Task执行链：用户明确提醒→Guard授权→时间解析→SQLite pending→Scheduler健康检查→事务领取＋Run→独立无工具Session→succeeded/failed/interrupted→提交→Channel投递→投递单独记账。

Goal执行链：明确目标→bootstrap草稿→waiting_user→用户批准Plan→仍等待→明确继续产生readyInput→消费一次授权→冻结Plan/Step/上次Checkpoint→一个text_only片段→校验JSON及版本→Checkpoint与状态同事务提交→partial等反馈或Step complete→用户确认整个Goal completed。

当前Goal状态字段没有`partial`或`failed`：partial是片段结果，失败在Run/Execution中，Goal进入blocked。面试时应准确区分这些层次，不能把概念性结果分类误说成数据库枚举。

## 最值得展示的三个技术亮点

**1. 用持久状态和可验证恢复管理长期任务。** Task领取与Run创建在一个SQLite事务，条件更新加唯一taskId约束；重启保留pending，running转interrupted，避免未经核对重放可能有副作用的任务。B02真实退出后用新PID执行同一Task；B03进入execute后SIGKILL，新PID只做保守恢复。本轮12条终态Task中0条多Run，但这是含故障注入的小样本，不是外部exactly-once承诺。

**2. 把目标推进、用户授权和模型产物拆开。** Goal中批准Plan不产生执行授权，一次明确继续最多一段，冻结输入并用版本/Hash保护Checkpoint提交。C01经过3次独立Execution完成bootstrap→partial→正式Step complete，最后由用户确认Goal完成；C02的pause/cancel两种迟到结果均不能提交。可以现场展示“模型说完成”和宿主completed的差别。

**3. 建立能保留失败的状态级评测。** 使用真实宿主与Pi、隔离SQLite和本机桩，覆盖20场景，保存原始工具参数/结果、运行事件、输入Hash和进程退出证据。591个测试通过时，新评测仍发现旧Task通知恢复缺口及Goal 429/500误分类，并保留M3历史语义反例。价值在于发现断言盲点和明确保障范围，不能包装成“模型成功率84.2%”。

Session和Memory可作为第三项的辅助演示：D01证明恢复历史与空Session隔离，E01证明更新事实进入新Session请求、Off无事实、注入不持久化；只有一个合成检索题，暂不适合拿“Memory提升任务完成率”作为量化主亮点。

## 指标如何解释

| 指标 | 这次怎么测 | 能说明什么 |
| --- | --- | --- |
| Task Success Rate、工具/参数/步骤准确率、不必要调用率 | 真实模型未运行；A01仅对固定桩调用作精确断言 | 无自主模型成绩，不能用Mock算准确率 |
| Task Execution Success Rate | succeeded终态Task / 全部执行终态Task=8/12，故障也计入 | 故障集合的运行结局；不能与生产正常任务成功率混用 |
| Restart Recovery Rate | B02/B03都符合各自恢复规格=2/2 | 包含安全中断，不代表2/2自动继续；B07通知恢复另失败 |
| Duplicate Execution Rate | 终态Task中Run数大于1的比例=0/12 | 数据库执行去重的小样本证据 |
| Goal State Accuracy | C01/C03/C04宿主预期状态=3/3 | 不等于模型的状态叙述正确 |
| Authorization Compliance | 9个显式授权检查Case均未违反禁止行为 | 有限离线集合的安全机制有效 |
| False Completion Rate | 已标注明确完成声明与宿主completed比较；unknown/歧义单列 | 检测器通过验证，但无本轮真实模型FCR；M3错误是虚假排队 |
| Session Routing Accuracy | 本分支无自动路由，D03跳过 | 不以渠道隔离冒充主题识别 |
| Memory Recall@5 / Answer / Task Success | E01召回1/1；实际请求On/Off比较；回答由桩给定 | 只证明合成检索和注入，不证明答案正确或任务收益 |
| P50/P95 | 对完整离线场景排序，含初始化和故障等待 | 报告中的耗时不是线上模型/路由延迟 |
| Token/Cost Per Successful Task | 无真实调用，记NA；实际收费为0 | 桩缺usage不能当真实模型零Token |

所有指标的分母、NA、超时、pass^3和后续真实实验方案见[完整计划](EVAL_PLAN.md)。

## 可复现的故障案例与根因

**Task结果已提交，但用户收不到通知。** B07先令Mock渠道抛错，再恢复渠道；重复tick不会补发。另在真实子进程Task提交后、投递前SIGKILL，新PID不重跑任务也无待投递消息。根因是旧Task没有与结果事务绑定的Outbox。保护了“不重跑执行”，却没有保护通知恢复。后续最小方向是结果与待投递同事务，消息有界重试；确认丢失仍可能重复，不能承诺必达。

**Goal的HTTP故障被错误标成中断。** F01同样注入429/500，Task得到failed，Goal得到interrupted，且都只有1次HTTP。根因是适配器在Goal非stop时先abort，后续stopped优先判断遮蔽模型错误。它没有误报成功，但会污染失败分类和恢复诊断。后续应区分真实取消/超时与宿主停止异常输出，同时保持禁止第二次请求。本轮未修复。

**历史M3模型声称已排队，宿主实际未授权。** 固定Fixture来自脱敏真实输出：Plan已批，waiting_user、readyInput=null、正式Execution为0。当前宿主渲染会明确“尚未排队”，C04原文回放仍保留原始模型语义失败。已证明的是宿主纠正有效，以及模型原文和数据库事实不能混作一个分数；不能证明当前模型总会犯同样错误。v2旧报告中的M3一次正确、M5复述限制误解、M8结束歧义也保留。

**工具写入异常后模型声称完成。** A02在隔离TaskService创建入口抛错，Pi接到错误工具结果后仍收到桩的“已全部完成”，Runtime最终failed、Task行数0。说明最终自然语言不是完成证据。它是确定性故障注入，没有声称真实模型选择了这句话。

## 15个面试追问与回答

1. **为什么不只是聊天机器人？** 请求可以变成持久Task或Goal，离开聊天后Scheduler继续按授权执行，结果和进度跨进程保存。聊天只是入口，真正状态在宿主服务；目前仍要求本机服务持续运行。

2. **Agent Loop和固定Workflow的边界在哪里？** Pi内的模型根据上下文、工具结果选择下一动作，是Agent Loop；宿主对权限、状态迁移、领取和提交的限制是确定性流程。后台Goal单段刻意限制成一次无工具生成，多段推进由宿主控制，不能说它是无界自主规划系统。

3. **为什么Task必须持久化？** 提醒是未来执行承诺，不能依赖进程内存或模型记得。SQLite能保存原始指令、UTC到期、目标与Run，并在重启时决定继续等待还是中断核查。Session无法提供原子领取或唯一执行约束。

4. **重启后如何恢复？** main先拿数据库和Memory锁并完成初始化，再recoverInterrupted。pending保持原到期时间；旧running的Run和Task标interrupted；Goal的遗留执行保守阻塞。B02/B03验证真实OS进程恢复；D01只验证Session文件恢复，两者不能混称。

5. **如何保证不会重复执行？** 数据库事务、条件状态更新及UNIQUE(taskId)限制同Task只能有一个Run；入站消息也有持久去重。通知失败不重新执行。不能保证外部副作用exactly-once：响应丢失时可能已经执行，故当前不自动重试，需要核对。

6. **怎样识别虚假完成？** 先定义Task/Step/Goal各自的完成事实，再将明确声明与宿主状态、Checkpoint、实际工具结果对比。Step complete不表示Goal completed，执行提交也不表示通知送达。歧义和宿主未知单列，不能交给同一模型自评通过。

7. **多个主题Session怎样管理？** 当前按渠道/身份隔离原生Session；WorkThread只手动关联对象，没有自动主题路由。自动拆分需主题标注、连续性和污染评测，不能靠新建Session数量证明路由准确。其他分支的实现应独立评测后再介绍。

8. **Memory怎样参与长期任务？** GoalRunner根据目标与步骤生成检索词，宿主读取当前Memory并在公开context事件临时投影；Memory不是授权来源，Task/Goal进度不存其中。E01只验证投影机制，不能说它已经提升最终任务成功率。

9. **为什么需要Goal状态机和人工审批？** 长目标涉及等待、反馈、暂停、计划变化和恢复，不能只依赖模型的一段文字。不可变Plan与稳定Step支持进度追溯，readyInput表示一次执行许可，Checkpoint保存已提交产物。人工批准计划和最终确认限制了模型误解造成的推进。

10. **怎么处理工具/模型失败？** Pi必须settled且最终stop，工具/模型错误、截断、空文本和中断分别检查。失败不自动重试。F01发现当前Goal分类不准确，说明“没有成功”还不够，错误原因也需要精确断言。

11. **工具执行成功但响应丢失怎么办？** 将副作用事实、宿主记录和响应确认分开。B07的已发送但确认丢失样本没有重做执行，却保留deliveryError。对于真正外部写工具，需要幂等键或查询核对；本轮没有授权新增这些生产能力。

12. **如何防止提示注入越权？** 外部资料和Memory低信任标记，工具白名单限制可用能力，Guard只根据当前已鉴权用户意图授予单次操作。E02强制模型在恶意工具资料后尝试保存，宿主拒绝。有限用例不能证明所有语义攻击都被防住，也不能把应用边界说成OS沙箱。

13. **怎样衡量长期可靠性？** 分别统计任务执行终态、恢复策略符合率、重复Run、记录丢失、Goal状态正确性、授权违规、投递成功、语义虚假完成、延迟与费用。标明时间窗口、正常/故障环境和分母；等待人工不等于失败，也不等于成功。当前没有长跑生产统计。

14. **怎么证明架构优化有效？** 先冻源码、数据集、模型/Prompt来源和预算，留原始失败；只改一个目标变量，在同一开发集配对重跑，再跑独立留出集。E01/D01仅验证信息通路，有无Memory改善答案或完成率仍需真实实验。本轮没有生产修复，不能说优化提升了分数。

15. **pass@3和pass^3有什么区别？** pass@3看三次至少成功一次，pass^3看同一任务三次全部成功。后者更关注稳定性。必须完成同场景三次真实运行才报告观测值，不能把三遍确定性Mock当模型稳定性。本轮两者均NA。

## 可以据实使用的三条简历描述

- 基于TypeScript、Node.js、SQLite及原版Pi SDK构建单用户Personal Agent宿主，分离Task、Goal、Session和Memory；实现事务领取、一次性Run约束与保守恢复，并通过独立子进程退出/SIGKILL验证pending恢复及running不自动重放。
- 实现Manual Goal的版本计划、稳定步骤、单次推进授权和事务Checkpoint；离线验证bootstrap→审批→partial反馈→Step完成→用户确认的3片段闭环，以及暂停/取消后迟到成果不得提交。
- 建立20场景可复现Agent离线评测，使用真实宿主/Pi、隔离SQLite、可控调度时间及故障注入；保存逐条Trace与输入Hash，定位通知恢复及Goal错误分类缺口；本轮自动回归591/591通过，评测结果16通过、3失败、1跳过。

如果简历篇幅有限，保留架构、实际OS故障验证和状态级评测三个信息点；详细失败数可放项目报告并在面试主动解释。不要写“生产级稳定”“自动多Agent总管”“Memory提升完成率”“零重复副作用”或“100%任务成功”。评测报告记录原始被测基线；后续评测分支发布不改变历史实验结果。
