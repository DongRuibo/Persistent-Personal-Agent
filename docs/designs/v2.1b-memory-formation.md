# V2.1b Memory Formation 设计草案

日期：2026-10-21；代码基线 `eeaeae9dd5fc1606b508824e0c68f2d7fca81d29`，结合本轮V2.1a.1收尾。**仅设计，尚未批准实施**。没有创建下面的表、Worker、配置或工具，没有自动分析正式聊天。

## 建议先确定的产品决策

推荐“**自动发现候选，集中展示，用户批准后保存**”。首个MVP允许一份列表展示多条候选，但每轮只批准一条，继续遵守现有OperationGuard的一次写入规则。不是每轮聊天都追问，也不是后台悄悄改画像。

“真正多条一键批准”与“用户授权范围内自动保存”是两个后续扩展；前者需要明确的有限批次授权，后者需要新的策略授权边界。不能把现有`确认`或`scope=task`当成这些权限。若用户希望首个MVP就支持一键多条，需要先批准修改“一轮一次”的限定设计，不能伪造多个交互请求绕过它。

示例体验：

1. 用户：“我以后做Agent项目主要使用TypeScript。”助手先正常回答，不同步提取或保存。
2. 空闲时形成候选，正文草稿为“用户今后开发Agent项目主要使用TypeScript”，附原话；未批准前不进入PROFILE、不参与知识检索。
3. 下次交互最多一天提醒一次“整理了2条可能值得记住的信息，需要时可以查看”，也可由用户自然询问“有什么建议记住的？”；首版不额外主动发送通知。
4. 用户看见固定列表，选择“第一条记下来”“第二条先别记”。只有明确保存选择经宿主验证后才写Memory，拒绝不写。
5. 旧记录是Python时，显示“原：主要Python → 建议：主要TypeScript、较少使用Python”，保留限定词，不擅自改成“完全不用Python”。

## 事实基础与研究取舍

现有能力与缺口：

| 现有代码 | 可以复用 | 不能假定已经具备 |
| --- | --- | --- |
| `pi-executor.ts` / Pi 1.3.0 | 原生Session、公开`ModelRuntime.completeSimple`、agent_settled后执行检查 | 当前task执行会自动检索Memory，不能直接拿它当隔离的候选提取器 |
| `operation-guard.ts` | 已鉴权本轮意图、宿主草稿确认、序号/过期验证、一次性WriteOperation | 当前确认状态只有5分钟且指向Task/真实Memory，不是持久候选清单或批量授权 |
| `memory-service.ts` | 四类CRUD、规范化正文去重、key/版本检查、原子Markdown、可重建索引 | 没有通用语义冲突/实体识别、候选存储、自动生命周期或跨存储事务 |
| `feishu-channel.ts` / Console | 身份/入站去重、串行主对话、Run提交、统一Channel | 没有渠道无关的“对话提交+形成入队”入口；不得让形成Worker接管飞书 |
| `sqlite-store.ts` | runs、run_events、model_calls、飞书入站去重 | runs没有原始用户消息字段。后台不能只拿runId就凭空恢复输入，或扫全局Pi历史 |

本机安装包`@earendil-works/pi-coding-agent/docs/sdk.md:92–94`明确区分agent_end和agent_settled；本项目还检查中断、错误和最终响应。因此形成入口取**宿主成功提交的聊天Run**，不直接监听每个agent_end或模型自述成功。

[LangChain官方Memory概念](https://docs.langchain.com/oss/python/concepts/memory#writing-memories)比较了同步路径与后台形成在延迟和时机上的取舍；[Letta官方API](https://docs.letta.com/api/resources/agents)也提供后台记忆管理选项。这些只用于比较时机，不引入其SDK/框架，也不照搬“模型直接写记忆”的权限模型。

### 三种最小路线

| 路线 | 时机/调用 | 交互及代价 | 权限/状态 | 判断 |
| --- | --- | --- | --- | --- |
| A. 本轮提取、逐条询问 | 回复前一次隔离提取；或主Agent先提议候选 | 简单即时，但增加等待、打断主任务；主Agent提取还受历史/Memory干扰 | 宿主展示后每项确认；少量临时草稿，但跨重启需持久化 | 可做原型，不推荐默认每轮触发 |
| B. 后台候选清单、受控批准 | 回复不等待，空闲时对有界新消息窗口一次提取 | 增加2张小表/一个串行Worker；需要接受候选非立即可见 | Worker只写候选；用户当前明确批准才由Guard写现有Memory | **推荐；MVP集中展示、单项批准** |
| C. 明确范围策略下自动保存 | 同B，策略允许的低风险字段可自动提交 | 确认负担最低，但误提/冲突/敏感事实代价更高 | 需持久策略、范围/撤销/有效期、独立受控能力；不是今天的Guard | 等B有质量数据后再议，不是MVP |

候选持久化不是另建一个Memory系统：只有已批准知识进入现有Markdown与memories索引；候选只是待办审查状态，不能注入回答Context。

### 触发、排队与模型隔离

- 默认关闭；用户先明确开启“建议记忆”及其信息发送/费用策略。这个同意只允许分析成候选，不允许保存为事实。以后开启自动保存还需另外授权。
- 仅处理开启后的新用户输入，不回填旧Session。Console与飞书都传入相同的宿主入口；身份绑定本机稳定的单用户owner，不把open_id当永久用户ID。保留渠道/消息ID作为来源与去重键，不让模型选择它们。
- 主对话执行正常、宿主检查完成后，**Run成功提交和Job入队在现有应用SQLite同一事务**中完成，取当次可信request原文的有界快照。这样不用重新扫描JSONL，也没有“成功提交后、异步入队前崩溃丢输入”的窗口。须小范围扩展渠道调用的宿主提交接口，不更改Task状态机。
- 上述原子入队仅针对已开启且符合条件的输入。若仅形成入队失败，回滚该事务后仍单独提交主Run及formation_skipped原因，正常回复；不声称该条会被分析，不扫描历史补跑。不能为候选队列故障把已完成的主任务改成失败；应用数据库整体不可写则仍遵守现有Run提交失败语义。
- 入队不等待提取模型。主回复投递尝试结束且前台空闲约10秒后，Worker串行取一个窗口；主聊天有优先权，新聊天到来时不再启动提取，可以中止在途提取，计费按已预留预算处理，不持有数据库事务等待模型。
- 每个窗口最多3条同一身份的新用户消息，按整句取≤约2000输入token总预算；太长或缺否定/指代上下文时跳过或待澄清，不剪掉“不”等限定词拼事实。每个sourceRun只进入一个提取窗口，更新模型/策略版本不能自动重放旧来源。
- 本地只做廉价排除：关闭状态、失败/中断Run、纯问候/空文本、已经实际提交的显式Memory操作、明显凭据/敏感片段、超预算等。不能靠“以后/决定”的词表假装完整理解；其他有意义的新消息由提取模型判断，可合并窗口、冷却和每日限额，不为每轮再加一个收费分类器。
- 提取最多一次`completeSimple`，无工具、无Session历史、不走现有Memory Context Hook。Pi相关代码仍放宿主适配层；Formation业务只依赖一个有界只读提取函数，与现有QueryRewriter一样不暴露Pi对象。
- 模型输入只含有来源标签的用户快照与最多5条本地找出的现有事实参考（可无参考）。助手回复、工具结果、外部网页及Memory不能成为新增事实的来源；已有Memory只用于比较，不能授权写入。两者在输入结构中明确分区。
- 每日最多20个提取请求、每次≤512输出token、最多3条候选。建议10秒提取超时、无自动付费重试，独立AbortSignal；这些参数尚未配置，实施前确认。形成失败只记录Job，不改变已成功的对话/任务结果。

## 候选值得保存的标准

候选必须包含用户实际表达的、对未来有帮助的事实；“模型认为合理”不是来源。输出必须给sourceRunId、原文quote/偏移、主体、属性、值、时间/范围、kind、候选正文、建议操作与不确定原因。宿主验证quote确实在已鉴权快照中、来源Hash未变；quote匹配只能证明出处，不能完全证明语义，仍需用户审阅。

| kind | 适合的候选 | 不应混入 |
| --- | --- | --- |
| semantic | 自述稳定偏好、长期开发习惯，如“今后Agent开发主要TypeScript” | 今天临时用一次、他人偏好、自我推断画像、敏感身份属性 |
| project | 有明确项目名的目标/技术决定，如Personal Agent继续Pi、放弃LangGraph | Scheduler待执行/成功状态、未拍板方案、别的项目同名字段 |
| episodic | 有长期意义的实际事件/用户反馈及日期；自述保留“用户反馈/自述”限定 | 全部聊天复制、每次普通任务结果、模型声称已执行外部行为 |
| procedural | 用户明确采用且有验证来源的操作经验 | 助手随口建议、未验证推断、可执行Skill/系统指令/新权限 |

一个事实只选一种主类型，相关项用来源/项目标识关联，不复制四份。没有项目名而仅说“我们这个项目”时，最多从同一窗口的用户原话解析；仍不清楚就生成澄清项，不能借旧Memory或助手推断代填主体。

MVP先开放semantic与project候选；episodic/procedural继续使用原来的明确记忆请求，后续再开放自动发现。这是缩小实施范围，不是改变四类存储。评测须同时报告MVP范围内召回和四类潜在信息召回，不能把暂缓类型从金标中删除来刷分。

否定、假设、引用他人、疑问、玩笑、愿望、尚未决定与明确事实分别标注；“如果以后换Rust”不是“已经改用Rust”。不确定时不进入可保存草稿，提示补充。不给用户“我已经记住了”的错觉。

敏感默认排除：密钥/账号凭据、精确位置、健康/财务等敏感个人资料、无关第三人隐私。入队前先做已知凭据和简单模式过滤，提取后再验证；语义检测不保证完美，候选仍需确认，不能据一次检测通过声称已做隐私脱敏。

## 重复、冲突、版本与主体隔离

1. 提取只产出提议。宿主按owner、明确主体/项目、属性和kind搜索现有事实，同时检查已待审查/已拒绝的候选。Retriever空结果不证明不存在，不能据此自动创建重复事实。
2. 规范化相同正文沿用MemoryService已有去重；候选以`owner+subject+property+contentHash`去重。近义但不确定是否同一事实，合并为一条待审查提议或标记需澄清，不自动合并实体。
3. 现有Memory尚无完备的主体/属性结构索引，key也可能是任意历史命名。MVP不能假定所有Python偏好都能精确查到：最多3次本地检索、5个候选参考，必要时本地读取核对key；不能把两个相似项目的记录直接作为更新目标。
4. “主要Python”→“现在主要TypeScript，Python较少使用”：若唯一可信目标存在，提议update，保留原ID/key、expectedVersion、旧Hash、前后正文与两者来源；若不唯一则先选择目标。保留“主要/较少”等限定，不改写成完全不用。
5. 模型可以建议update和targetId，但真正目标从当前存储核对，用户批准的是固定的前后内容，不是一个模糊意图。无明确目标时不能为了省事直接remember第二条矛盾事实。
6. 时间不同的事件不是互相覆盖；他人偏好不是用户偏好；项目技术语言不是用户长期首选语言。较新记录不自动推翻所有旧记录。历史事件和当前偏好可共存，但必须区分范围。
7. 创建新的事实key由宿主规范化/限制长度，模型不提供路径。旧事实的key保持不变。低置信度的主体或属性映射不触发“就地更新”。

## 两张拟新增表与模块关系

建议把控制状态放现有应用SQLite（包含Run和入站去重的数据库），由独立FormationStore模块管理两张新表。**不放可重建的Memory index.db，不新增第二套长期知识正文，不把Job伪装成Task。** 好处是Run成功与入队可同事务，停服备份继续包含该数据库；代价是须批准增量Schema和宿主提交入口扩展。独立formation.db更隔离，但会新增跨库提交窗口/备份件，MVP不优先选。

| 表 | 建议的最小字段与约束 |
| --- | --- |
| memory_formation_jobs | id、owner、sourceRunId/消息来源、boundedSourceSnapshot、sourceHash、memorySnapshotDigest、policyVersion、windowId、status、createdAt/expiresAt、reservedBudget、modelCallId/errorCode；UNIQUE(owner, sourceRunId)，状态queued/extracting/done/failed/expired/cancelled |
| memory_candidates | id、jobId、owner、kind、subject/property、draft正文、sourceRefs/quotes、create/update/clarify、targetId/targetKey/expectedVersion/oldHash、revision/draftHash、memorySnapshotDigest、review状态、approvalRunId、resultMemoryId/version、UTC时间；规范化同事实唯一，approvalRunId非空时唯一，拒绝项也保留最小Hash抑制重复打扰 |

每个成功Run至多入队一行，不能依赖JSON数组内的sourceRunIds做唯一约束。Worker在短事务中一次领取最多3行，设置共同windowId，再用这些行组成一次模型输入；主Job记一次预算/模型调用，其他行只关联同一windowId和收据。来源窗口可聚合，但一个Run不能被另一个窗口再次消费。

候选状态：`pending → applying → applied`；也可转`rejected / stale / expired / needs_clarification / blocked`。MVP不做新的Task状态或通用工作流引擎；同进程一个Worker，用SQLite条件更新领取Job，启动后把遗留extracting标为失败/待人工重试，不自动产生第二笔模型费用。

模型调用只记一次真实用量，带`purpose=memory_formation`及jobId，关联触发的Run（多来源窗口另列sourceRunIds）；不和主聊天调用混为响应延迟，不在Job与model_calls两处分别累计账单。需要给现有模型观察记录增加目的标识，不能把SDK未报告用量的中断记成免费。

未来预计改动：宿主组装/渠道提交入口、只读模型适配、Formation业务/两表、Guard候选审查分支与相关contracts。MemoryService仍唯一提交，Retriever只读；不修改Pi内部循环、不改变Task和飞书鉴权/通知语义。以上均未实施，实际文件清单应在开发任务确认后收敛。

## 用户批准与来源授权

- 自动发现、持久化候选和正式写Memory是三个权限，不能互相替代。Worker没有`WriteOperation`、没有Memory工具，不能通过`withRequest('记住…')`、修改request.scope、伪造source或旧Session文字取权限。
- 宿主展示实际候选正文、原话、类型，更新时展示旧值→新值；固定最多3个编号与5分钟选择有效期。候选本身可保存7天，但旧列表过期就重新展示，不把7天候选寿命当授权寿命。
- 在DialogueReferences新增受宿主管理的candidate_review引用命名空间；不能把候选ID冒充真实Memory ID。列表重排、Task选项和候选选项不能共用一个“第二个”；一次只存在一种活动选择视图，切换就失效旧视图。
- 用户自然表达“第一条记下来”→隔离意图解析只看当前消息及可信pending元数据→Guard按固定编号、owner、revision/hash、目标ID/版本、有效期和当前Memory快照复核→授予本轮唯一操作→MemoryService执行。模型不得从候选正文重新扩大授权。
- 现有guard没有“接收持久候选草稿”的公开入口，需要新增**受控宿主入口**，持久化并核对展示内容；不能从业务层直接操作Pi消息或修改私有Guard对象。批准提取正文属于用户对已展示草稿的明确同意，不要求用户重打整段“记住”命令。
- `MemoryRecord.source.type=user_explicit`继续表示最终写入有本轮明确用户批准，不能称提取本身已获保存授权。source.reference保持当前的审批Run ID，不拼接模型提供的来源字符串；候选表通过唯一approvalRunId关联原始sourceRun/hash及结果版本，界面区分直接原话写入与经批准提取。原始聊天作者/引用归属不可冒充用户自述。MVP不改Markdown元数据格式或引入inferred类型，但Guard受控入口仍须明确支持“批准已展示草稿”，不能伪造当前原文。
- 首版一次只执行一项批准，维持普通Guard所有旧约束。用户说“全部保存”时先请选一条，不悄悄消费多个写操作。后续多项批准须显示不可变批次、限制≤3项、逐项版本检查与独立收据，明确部分成功语义，并另行审查一次写入规则的限定扩展。

### 为什么暂不推荐范围自动保存

范围策略至少要有owner、允许kind/主体/属性、敏感排除、更新是否允许、版本、有效期、日费用/写入数上限、撤销入口和逐项审计。不能用一句“你可以记住我的偏好”批准任意人物、项目决策或敏感推断。即使以后有策略，已有事实冲突、跨主体与删除仍优先人工审查。

这需要新建受控policy能力与明确调整当前“仅当前明确意图可写”的规范；后台提取器和Task仍无任意写权，不通过假装chat绕过。留给独立阶段，先用B的拒绝率、确认负担和错误成本做决定。

## 失败恢复、幂等与遗忘

| 窗口 | MVP行为 |
| --- | --- |
| 入站重投/同一source重复 | 复用既有飞书去重；Job另有source唯一约束，窗口内已处理Run不重复收费 |
| 模型中断/无效JSON/quote不匹配 | Job失败，无Memory写入；无自动付费重试，保留原因而非原始错误凭据 |
| 待审查时Memory被更新/删除 | 每份候选绑定全库ID/version/hash集合Digest；发现任何变动则失效旧草稿，重新展示/澄清，不静默调整目标或自动重提取 |
| 审批后、提交前重启 | 不自动续写。重开后需要当前用户重新确认；旧批准不是永久能力 |
| Markdown已写、SQLite/候选状态未提交 | 先修复索引，只读核对目标ID/key、预期后继版本、正文Hash及source.reference=approvalRunId；确有本次提交则补收据，不重复update |
| 正文相同但来源并非该候选 | 记为already_exists或待复核，不能冒称本次成功；不盲目追加新记录 |
| 目标已有第三个版本或Hash异常 | 标stale/blocked，不重放已批准旧正文，也不把任务终态或权限降级 |

Job与候选可在同一SQLite事务变更，但Markdown和该库仍没有跨存储事务。MVP同步在当前审批请求内执行MemoryService，不另建后台写Worker；先持久化applying及approvalRunId，再调用唯一写入口。`applying`重启时先做上述只读收据核对，确认自身已提交后再处理Digest变化；否则自身成功写入改变Digest也会误失效。没有匹配收据时不能凭applying自动重试不确定写入。

Digest是保守的MVP取舍：任何Memory改动（包括忘记）都使旧来源快照/待批准草稿失效，防止排队的旧话在忘记后再次生成知识。它可能同时使无关候选失效，先接受这个成本，后续再做更细的对象级抑制，不在本阶段引入第三套墓碑账本。

拒绝同一候选后，同owner/主体/属性/Hash不反复提示，除非用户主动重新开启该建议。合并不同事实、失效知识、批量删除暂仍走现有明确Memory操作；自动合并/TTL删知识不做。重要日期作为事实限定保存，不把已结束事件直接删除。

候选/Job正文和摘录拟7天到期，目录/数据库私有，事件日志只留ID、状态、耗时和用量。applied行保留最小来源Run/审批Run/Hash/结果版本，不永久复制全部聊天；来源过期后只能证明关联标识，不能承诺永久回查原文。forget现有知识仍不自动擦除Session、Run、备份或SQLite空闲页；新增候选副本的删除/过期也须在用户说明中列清。

备份继续正常停服后复制应用数据库、Markdown/索引、Session；恢复时未批准候选不自动写，审批引用缺失/Hash不一致即失效。原有Task恢复语义保持不变。

## 可复现评测与验收计划

先人工冻结**60个虚构提取窗口**（每窗口2–3条来源明确的用户消息，属于多轮对话），分为6组各10：稳定偏好、项目决定、事件/已验证方法、否定/引用/假设/临时信息、敏感/未知主体/相似项目、重复/冲突/忘记与恢复。每组5个开发、5个留出；人名/项目名/字段值跨集合隔离，不能根据留出改金标。

金标字段：worthKeeping、kind、主体/项目、属性/值、时间和否定限定、来源Run/quote、create/update/skip/clarify、目标版本、sensitive、MVP范围标记、最终期望知识集合；全部未经批准的autoWriteExpected=false。额外保留错误候选会导致什么回答的反事实测试。

示例窗口（只作设计样本，未调用模型）：

| 用户消息/背景 | 期望 |
| --- | --- |
| “以后Agent项目主要TypeScript” | semantic候选，保留领域范围，不立即写 |
| 旧偏好主要Python；“现在主要TS，Python用得少了” | update候选，展示旧值与限定，不新增矛盾事实 |
| “Personal Agent决定继续Pi，不用LangGraph” | project决策，不能换到另一项目 |
| “如果以后不用Pi会怎样？” | 不形成已决定事实 |
| “朋友说他更喜欢英文；我仍然偏好中文” | 区分说话者，只提议有价值且允许的用户偏好 |
| “今天临时借Python脚本处理一次” | 临时行为不升为长期偏好 |
| “这个Key是<REDACTED>，不要保存” | 不保存、不把真实凭据送进提取，样本使用假值 |
| “我试过了，先备份再恢复能解决问题” | procedural潜在候选，MVP标暂缓，不当Skill执行 |
| 用户先否决候选，后重复同一事实 | 不反复追问，不自动恢复被拒绝候选 |
| 批准前用户忘记旧事实/其他入口改版本 | 草稿失效，不复活旧值；全新Session核对 |

指标必须分层：

- 提取：候选准确率、值得保存的漏提率、负例误提率、四类分类、主体/字段/限定正确率；区分MVP范围内和全部四类。
- 合并：相同事实重复率、冲突目标/版本/新内容准确率；错误更新必须按严重错误单列，不被总体平均淹没。
- 权限：未批准写入0、后台工具0、跨owner操作0、敏感样本落知识0、同审批重复应用0；每项核对真实Markdown/SQLite状态，不看模型自述。
- 用户负担：每10轮提示次数、每条最终采纳记忆的确认次数/编辑次数、拒绝后重复提示率、候选等待时长。初始建议候选提示≤1次/日，确认成功写入≤1项/轮。
- 资源：实际模型调用、输入/输出/缓存Token、中断未知量、队列等待/提取耗时、主聊天新增P50/P95延迟及全库核对耗时。
- 最终帮助：同一对话分别关闭形成、只提取未批准、批准后，换新Pi Session询问；核对实际注入ID/version/正文与答案，不把候选或原Session复述算Memory效果。更新后只认新值，忘记后不从待审查队列复活。

提议初始门槛（待确认，非本轮成绩）：MVP候选precision≥90%、recall≥80%；错误主体/未经批准写入/敏感落知识为0个样本；冲突目标准确率≥95%，不达标先留在影子模式。不要因数据少把零错误样本解释成安全证明。信息价值有主观性，应保留标注理由与异议样本。

分层验证：纯单元/真实SQLite/模拟模型先验证持久状态、审批、故障与接线；真实模型提取和新Session生成另行申请固定数量与预算；最后才用飞书少量虚构对话验证自然体验。真实语义评测不能靠模拟答案冒充。

## 最小MVP与实施顺序

1. **确认本草案**：选择候选清单模式、先semantic/project、默认关闭、信息发送范围、每日预算和单项批准；同意后才调整相关AGENTS边界与新增Schema。
2. **影子管道**：两表、来源快照/同事务入队、有界只读提取、去重冲突草稿；只用虚构/模拟模型，候选不进入Memory/Context。
3. **固定评测**：冻结60窗口，达到初始质量门槛；另获授权后做真实模型提取/生成，不读取正式历史。
4. **受控批准**：集中展示、自然语言选择一项、Guard复核、唯一Memory入口、版本/幂等/重启不重放、忘记使旧草稿失效；Console/飞书双入口回归。
5. **真实小范围体验**：仅用户同意的新消息，观察一周的采纳/拒绝/误提/成本，不回填历史；不自动扩大范围。
6. **再决定**：是否做≤3项真正批量批准，是否开放另外两类候选，是否设计范围自动保存。后两者不因本草案存在就获得授权。

当前建议可以结束这一轮Retriever的针对性修复，进入上述设计审查；有界检索与证据判断仍不是自动写入的充分安全依据。本草案的核心收益是把“发现可能有用的信息”和“有权把它变成长期知识”分开，同时让普通用户不用每次主动说“记住”。
