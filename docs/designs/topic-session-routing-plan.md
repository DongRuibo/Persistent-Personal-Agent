# 持续主题与独立会话实现规划

日期：2026-11-03。状态：方案待用户批准；本次只规划，不实施业务变更或切换试用实例。

目标是让同一个 Personal Agent 在一个对话框里，自动接续健身、求职、具体项目等持续主题的上下文。日常短文、解释和临时改写可以直接完成；属于既有主题的小问题回到该主题，不为每份交付物建立主题。选择上下文与创建后台工作是两个独立决定。

## 2 产品行为

| 场景 | 应有行为 |
| --- | --- |
| 写一句生日祝福、解释概念 | 日常Session直接回答，零新主题、零新Job |
| 已有健身主题时询问训练或饮食 | 复用健身上下文，不按“训练/饮食”分别建主题 |
| 求职过程中修改自我介绍 | 留在求职主题；普通文字改写直接答，明确修改已有Job成果时沿原Job续接 |
| 从求职切回健身 | 恢复健身Session的相关背景，求职正文不混入 |
| 两个不同代码项目 | 各自主题和Session；同叫“登录问题”也不能混为一个工作 |
| 首次明确提出持续事项且没有匹配主题 | 总管提出结构化新主题，由宿主创建关系和Session绑定；在聊天中轻量告知，不再要求用户先去工作台操作 |
| “这个计划改一下”有两个合理对象 | 问一个具体澄清问题，暂不执行、不创建新主题 |
| “这件事归到求职里” | 调整当前后续归属；不重写旧日志、不自动重放先前工具或工作 |
| “用项目经历改简历” | 求职仍是目的主题；不把提及的项目名当成切换命令 |
| 一条消息确实要求跨多个主题执行 | 第一版保留原话、问先处理哪个主题；不自动广播整段消息或新增多主题并行系统 |

第一版支持一个主题的一个当前持久Session；一个主题中仍可有多个Job/Goal。主题长期存在不表示Worker常驻，也不等于无限上下文。阶段Session轮换、自动主题合并/拆分、跨主题自动检索拼接列为后续。

表中的跨主题澄清规则仅适用于新主题模式；关闭新开关时，原Coordinator的多项请求处理保持原样。健身、求职和代码项目是验收例子，不是写死的主题分类。

## 3 最小架构

流程：Web接收并串行领取消息 → 有界主题路由 → 保存本次归属 → 对应主题或日常Session回答 → 必要时沿原work_manage和WorkRunner执行后台工作 → 同一时间线显示结果。

路由不负责写正文或执行任务。主题Session是该轮唯一交互主Loop；全局入口不再生成另一套答案或审批上下文。所有Session使用同一Pi公开SDK和原权限服务，不为每个主题复制一套Agent配置。

### 3.1 持久数据

优先增量扩展现有表，不新建业务正文或状态副本。

| 位置 | 拟新增信息 | 目的与限制 |
| --- | --- | --- |
| `work_threads` | `description`：简短主题范围；`chatContextKey`：可空的宿主逻辑Session绑定 | 复用稳定threadId、owner、channel、归档状态。简介只描述范围，不自动积累个人事实或取代Memory。逻辑key由宿主生成，模型不能给文件路径 |
| `web_ui_chats` | 接收时的主题模式标记；可空的已冻结route记录 | 保存daily/topic/clarify、threadId、contextKey、标题快照和简短路由依据；不复制原消息或Job状态。重投相同requestId只回读 |
| 原Pi Session JSONL | 该主题交互、原生压缩条目、该Session的DialogueReferences | 完整历史仍归Session；正式成果、执行和审批仍在原Run/Job/Goal存储 |
| 原run_events / model_calls | 路由与压缩的实际调用、结果及失败 | 沿用审计/用量体系，不增加日志平台 |

旧主题新增字段默认空/未绑定；不自动把之前每份短文对应的组织主题变成长驻会话。已有未绑定主题只有被用户明确选用为持续主题时才建立绑定。旧聊天不批量重分类或搬入主题。第一版既有已绑定主题优先复用；新主题只能来自当前用户明确的持续事项，不能从资料中的示例或模型猜测创建。

迁移只在临时SQLite验证。`work-thread-store.ts`现有无列名INSERT需同时改为显式列名；现有get/list返回字段和旧数据兼容性一并覆盖。

### 3.2 主题路由

新增小型 `topic-router.ts` 和类型定义，作为宿主调用的解析服务，不是给模型新增任意Session操作工具。

输入是当前原话、少量最近路由线索、当前有效指代，以及有权访问的主题名称/简介。没有所有主题全文、全局Memory正文或后台结果堆积。目录遵守已有候选数量/总字节边界；超过范围需要缩小候选，不能截掉其他候选后宣称唯一。

输出仅为四种：日常回答、使用已有主题、创建持续主题、澄清。用户明确纠正由“使用已有主题”附带可核对的当前引用处理，不新增一个通用规则学习系统。先识别“切换到某主题”还是“引用另一主题资料”，再判断归属；当前焦点只帮助省略指代，不能压过明确换题。

可明确绑定到消息/成果的引用先走宿主定位；其余需要语义判断时最多一次无工具模型解析。选定主题并不选中其中最近的Job/Goal，更不授予继续执行权限。候选ID、归属和解析格式只在入口校验一次，后续传类型化结果。

“确认”“就这样”等短确认先按当前界面已完整展示的具体收据和原引用失效规则定位；只有唯一有效对象时才能定位Session并交原Guard，歧义时澄清。进入/恢复主题不等于重新展示审批、不延长有效期。受原“其他普通Chat结束短确认引用”规则失效的引用，不能因切回主题而复活；需要时重新展示原审批。这里复用现有收据/展示事实，不另造主题审批体系。

路由先于主题主prompt，不能依赖主模型已经进入某Session后调用work_manage再决定本轮Session。解析计入同一用户请求现有的8次模型HTTP总上限；不能新增一套独立8次额度。解析失败/超时/无法定位时明确未执行，不偷偷切到日常Session执行原请求，也不自动收费重试。

创建主题与冻结route使用同一现有SQLite事务；先成功保存绑定，后首次打开对应Session。进程崩溃或相同UUID重投不重复建主题；已claimed的中断请求沿原恢复语义，不重放模型或工具。已接收的主题模式请求在开关关闭后保留等待/撤回能力，不能按旧模式重新解释；新消息走旧路径。具体字段在N1冻结，不能另造第二个消息队列。

### 3.3 Session与身份

当前 `chatKey` 同时决定Session目录和Web/文件owner，不能把它简单换成topicId。保持现有Web actor、业务owner和后台Executor不变，在Pi适配层增加独立的可信contextKey。

每个主题Session一起保存/恢复自己的SessionManager、DialogueReferences、Guard引用和工具回调；不能只切历史文件却共用审批焦点。全局GoalService只有一个displaySink，应把显示回执投递到当前请求所属Session，不为每个主题重复覆盖全局回调。主题身份独立于短期workFocus。

继续使用现有Web串行领取和Pi chatBusy门；按需打开所选主题，无常驻Worker、连接池或新并发调度器。Session路径由宿主根据已验证owner/contextKey构造，业务模块不传Pi对象或文件路径。

### 3.4 上下文连续性验证门

现版Coordinator只投影最近两轮普通文字、合计4KiB，且原生compaction关闭。仅增加Session文件不能让模型接上更早背景。

推荐先验证：在串行空闲边界、当前用户主prompt开始前，通过Pi公开 `compact()` 压缩该主题历史，保持auto-compaction关闭，避免溢出后的自动重试/续跑改变现有语义。主题路径使用压缩感知的当前Session上下文，不再套全局两轮投影；日常旧路径和Memory/Web低信任处理不扩大。

压缩触发同时考虑模型token窗口与现有65536字节宿主请求上限，预留当前原话、系统提示、工具Schema及Memory/Web临时投影；不能等模型窗口溢出才压缩，也不通过增大原上限解决。N0验证历史增长时前置压缩后实际HTTP payload仍符合原门限。单条输入本身无法容纳，或本轮工具结果增长后超限，继续明确报原失败，不在运行中的工具链中途压缩并自动续跑。

本机SDK 1.3.0静态核对发现，原生compact摘要请求不经过宿主现有before_provider_request计数，usage也不走普通message_end；split-turn可能发两次摘要HTTP。活动上下文还可能不含旧host开始标记，当前投影会丢摘要。**这是真实待验证接缝，不能只把enabled改true。**

N0必须用假模型实际HTTP证明：路由、压缩、主Chat共用本次请求的预算、取消signal和绝对超时；全部压缩调用在发出前计数并受同一回合剩余额度约束，usage落原审计。split-turn第一请求成功、第二请求失败/取消时，已发生的调用和已知用量仍须保留，未知用量不能记作零。摘要与保留段没有丢当前原话/工具配对，授权只来自当前请求；压缩失败与重启不重放动作，完整旧记录仍可读取。只使用公开SDK入口、扩展事件和宿主适配，不修改SDK或Agent Loop。

原生compact直接读取Session原始分支，不自动经过主context投影。N0须检查实际摘要请求：Web原始工具全文不能绕过现有正文预算；来源和低信任身份需在摘要后保留，不能升级为指令/许可。临时Memory仍由原服务按本轮有效性读取，旧检索正文/版本不能经摘要冒充当前有效Memory；用户原本说过的话仍遵循原Session历史语义，不承诺forget同时删除聊天。若公开接口无法控制压缩输入并保留这些边界，同样在N0暂停。

如果公开接口无法满足这些要求，N0暂停并报告具体缺口与最小替代方案，重新确认后再推进；不得默默自建另一套摘要/记忆框架，也不得回退两轮窗口后宣称长期连续性已完成。批准本计划不等于批准任意替代方案。

### 3.5 后台工作与跨主题资料

在已选主题中创建新Job时使用该请求已冻结的threadId；Job标题不再决定主题。现有Job修订仍以rootJobId/previousJobId为准，不能因用户切换聊天主题而搬动或改写执行链。

日常Session中的一次性显式后台请求沿现有工作机制承接，但其组织主题默认不建立持久聊天绑定。已有工作仍可明确查询、修改和取消。主题聊天本身不触发后台工作，普通主题小问题直接回答。

现有主Chat、work_manage说明及隔离解析提示都把“持续/分阶段”作为工作候选，Goal提示也有“持续协助”的表达。新模式需要对齐这些提示：“以后在这里帮我健身/求职”首先建立持续对话上下文，不能仅凭持续性创建Job或Goal；明确安排需推进、管理的目标时仍走原Goal审批/执行流程。此调整限于新模式意图区分，不改Goal状态机、执行许可或关闭开关时的原行为。

第一版不自动从另一主题的Session读取正文。“用项目经历改简历”仍定位求职；已有明确成果可沿原Recall/对象授权引用，缺少合法定位时请用户提供资料，不复制另一个主题全历史。引用不改变本轮归属或操作权限。

| A3 | 训练、饮食、每周反馈 | 同一thread/contextKey；不因交付名称新增主题 |
| A4 | 两个代码项目各有“登录问题”，同主题另有两个Job | 路由与Job对象都正确；主题匹配不能代选最近工作 |
| A5 | 无唯一指代、首次持续事项、无关小问题 | 分别澄清、一次创建、日常回答；没有无依据新主题或动作 |
| A6 | 切换主题、引用别的主题资料、用户纠正 | 切换与引用区分；纠正不重跑旧模型/工具，不批量改旧日志 |
| A7 | 重投、路由落盘后强杀、正常重启、开关关闭与旧队列 | 无重复主题/工具；恢复绑定；已中断不重放；旧主题请求不降级执行到日常 |
| A8 | 错误/越权/归档ID、恶意简介；A展示待批→B展示待批→返回A/纠正路由→裸“确认” | 拒绝或澄清不明目标；只有原展示与有效引用才能批准，旧pending不能因恢复Session而复活；route不能成为Guard授权或新的渠道身份 |
| A9 | 历史增长至宿主字节门前、原生压缩、split-turn部分成功后失败/取消；带Web与失效Memory资料 | 实际payload符合原64KiB门；每次HTTP前检查同轮预算，已知用量留存、共享取消/超时；低信任来源与原正文预算不丢；旧检索不变当前Memory；原文/工具配对/原许可保持 |
| A10 | 后台工作进行时聊天、通知到达、刷新及窄屏 | 单入口可用；结果回原工作；通知/只读轮询不抢主题；无新必选控件 |
| A11 | 新开关关闭；原Task/Goal/Memory/Web/文件审批 | 原行为和既有回归通过，不能以新模式绿灯替代旧功能检查 |
| A12 | “以后在这里帮我健身/求职”与明确要求创建、推进Goal分别输入 | 前者仅绑定主题Session、零新Job/Goal；后者仍经原Goal工具、审批与许可推进，主题选择不代替目标管理 |

N5实际运行typecheck、后端build、web:build、全量npm test及适用离线浏览器流程，记录源版本/退出码，不相加不同组计数。确定性模型只能证明宿主机制；另保留少量真实自然表达的用户手动试用，用来验证分类、澄清频率和连续回答质量。

用户已允许复用本机既有四项模型配置、不设人民币额度；该授权不意味着Agent可自动发收费验收消息。新功能试用需明确切换到哪个隔离实例，保留现有试用；不触碰正式数据，也不自动发布。

## 7 主要风险与决策点

- **公开SDK压缩计量和宿主边界**：已有静态缺口，N0先实证；无法兼容则暂停，不做带隐藏调用的实现。
- **语义分错或主题过多**：优先复用、有范围简介、歧义澄清和可纠正；不能用纯mock测试宣称分类准确。初版不加Embedding、自动主题聚类或后台主题整理。
- **跨主题引用误当授权/焦点**：主题、工作ID、Goal和审批分开；当前消息仍是授权入口。两者相关不等于复制历史或合并身份。
- **上下文成本/延迟**：语义路由和必要压缩会额外调用模型；同轮预算统一，主题按需运行。先记录实际调用数与延迟，不先承诺更快或更省。
- **基线与试用混用**：开发树独立、旧实例保留；本轮实现批准不自动包含Git远端发布或正式环境切换。

方案批准后先执行N0，再按依赖推进N1—N5。常规修复和离线验收可在批准范围内自主进行；三轮审查未通过、公开SDK接缝不可行、重大架构替代或权限扩展时暂停汇报。

## 8 参考与适用边界

- [DeepSeek公开原型执行机制](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md)：工单与执行Session分离、后续续接；它是面向单仓库的研究原型，不能直接代表个人长期主题。
- [Letta Conversations](https://docs.letta.com/concepts/conversations)：同一Agent下独立会话的概念；我们不照搬其自动共享记忆策略。
- [OpenClaw路由](https://docs.openclaw.ai/channels/channel-routing)：借鉴稳定会话身份，既有channel绑定不等于语义主题识别。
- [Hermes委派](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)：临时独立子任务与长期主题需分开。

上述公开资料已在前一轮调研核对；本方案的具体模块与行为是基于当前仓库的设计选择，不宣称参考项目已经实现相同产品体验。
