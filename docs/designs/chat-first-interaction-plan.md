# 以对话为核心的个人 Agent 交互方案

日期：2026-11-02。状态：**待用户讨论与批准的方案，不是实施授权或已上线能力**。本轮只读核对当前代码并整理文档，沿用 Planner 协调、Worker 实现、独立 Reviewer 审查的分工。

> 后续校准：用户进一步明确了总管自动分派与具体工作上下文隔离的核心要求。[总管架构复盘](super-agent-alignment-review.md)修正本方案的架构与实施顺序。本文的简洁界面、真实状态和审批原则保留；C1+C2单独交付、旧成果留在主Chat修改以及复合请求统一只挑一项的安排，不再作为下一批实施依据。原R2审查记录属于当时文档，不能代替新架构批准。

## 1 最终要做成什么

此前产品路线图的核心目的仍然成立：**把一件值得持续关注的事交给 Agent，得到有依据的成果；下次回来能接着推进，有重要变化时才需要介入。** 原四阶段规划进一步要求它自行组织、关联和协调多项工作。

用户应该能够说：“帮我准备 Agent 面试，也跟进我的 Personal Agent 项目。”之后直接问“面试准备到哪了”“把刚才那份改短一点”“项目有什么值得注意的新变化”。Agent 负责找到正确的事情、读取真实进度、在已有授权内继续工作、交付成果，并在有歧义或需要新授权时问清楚。

这需要五种用户可感知的能力：能承接事情、能持续推进、能找回上下文、能交付成果、能有分寸地跟进。WorkThread、Router、Worker、事件和 Recall 是支撑这些能力的内部机制。用户不应先学会这些名称再使用产品。

长期方向包括离开网页后持续工作、日常移动入口和更多真实资料来源；当前仍是本机 Web、单一工作空间。电脑停止运行时服务不会继续工作，Web 与飞书也未共享身份与业务空间。这些不能由精简界面代替实现。

## 2 日常界面

打开即进入对话。底部只有一个输入框和一个发送动作，Enter 与发送按钮含义相同。输入区不再要求选择主题、对象、后台模式或路由模式。

日常导航保留“对话”“我的事情”，审批、来源、记忆管理和技术记录按需进入；原页面仍可复用，不为改入口重写整个 UI。“我的事情”只是现有对象的整理视图，不新增一套任务事实源。

对话里的工作卡示例：

```text
你：把下面这些面试笔记整理成复习提纲，突出薄弱点。〔完整材料〕

助手：已接下“面试复习提纲”，整理完成后会发在这里。
      面试复习提纲 · 正在整理              停止

你：顺便解释一下幂等是什么。
助手：……

助手：面试复习提纲已完成。
      这里直接显示提纲正文，长内容可展开。
      已归入“面试准备”                   查看详情
```

上面的接单文案只能由宿主确认持久化成功后出现；“正在整理”对应真实 running 状态，不是模型先说一句“我会去做”。结果仍引用原 Job/Run，不能为了出现气泡另造一次 Chat 执行。

工作卡默认只显示事情名称、真实状态和结果，必要时显示阻碍与下一步。无依据的百分比、模型虚构的内部步骤、UUID 和模型调用数不占主视图；技术详情仍可查看。Goal 可以展示已有计划和已提交步骤，单次 WorkJob 只能展示生命周期，不能伪装成有细分步骤的计划。

主题是可纠正的整理结果，不是发送前的表单。小问题不建主题；明确的新工作可以由宿主建立轻量主题，已有且唯一的工作上下文可以复用。多个旧目标可能被影响时，问“你指面试提纲还是项目报告？”；不让用户在所有请求前先选一次。

## 3 用实际场景验收体验

以下均为目标交互；“需补接线”不表示目前已经可用。

### 场景 A 简单处理直接回答

用户：“把这段虚构周报整理成三条待办：完成设计稿、补齐测试、整理发布说明。只整理文字。”

助手直接交付三条文字待办。不要创建提醒、Goal、主题或后台工作，也不要先问“普通聊天还是后台处理”。这次真实试用已经说明，任务承接方式不应该成为用户的学习任务。

复用原 Chat/Pi；需要修改的是入口和工具选择说明，并回归误调用工具后的行为。验收是一次发送拿到结果，新增 Router 请求为零，业务写入为零。

### 场景 B 较长的材料交给它做

用户粘贴完整笔记：“整理成面试复习提纲，指出薄弱点，每项附一个练习问题。”无需加“后台处理”四个字。

Agent 判断是否需要委派。若直接回答，交付正文即可；若委派，主对话显示已接单及真实工作卡，完成后同处交付全文。期间用户可以继续问别的问题。用户不必前往主题或收件箱才能拿到首次结果。

复用 WorkJobStore、WorkRunner、独立临时 Session、取消和重启规则；需新增受控 Chat 委派及对话投影。首批仅完整处理当前用户这一次提供的文字，一次请求最多一个 WorkJob；不拆成多 Worker，不传入聊天全历史，不让主模型自由改写 Worker 指令。

验收必须同时覆盖直接回复与受控委派两条路径。模型具体选择不以字数阈值硬编码，但“已接单”必须有数据库记录，“完成”必须有提交结果；不得同一请求同时完整做两份工作。

### 场景 C 接着刚才的成果做

用户：“把刚才那份提纲压缩成五个重点。”或“上次面试准备到哪了？”

有唯一、可信的当前成果引用时，宿主读取其当前有权内容，助手继续回答并附可展开来源。若有两个候选，在对话里问一个简短问题；用户可直接回复名称，也可点候选。没有命中时说明缺少依据，不凭 Session 中的旧文字编造进度。

复用 WorkRecallService、原对象归属检查、Goal committed 成果与 Hash 检查。需新增 Chat 只读查询工具、当前对象引用和有限上下文接线。现有 Recall 对没有明确对象的“刚才”会澄清；不能只加一段提示就声称解决指代。

首批这类改写在普通 Chat 中完成。把历史成果拼入新后台工作属于后续输入快照扩展，不能悄悄改变 WorkJob“只处理当前原文”的契约。新引用只供当前请求使用，按来源、字节预算、截断和低信任规则处理；不自动保存长期 Memory，也不把全部后台输出永久追加到 Chat Session。

验收要检查实际模型请求是否包含正确成果，以及来源、当前版本、截断是否正确；单纯看到结果气泡不算上下文接通。

### 场景 D 持续推进一件事

用户：“下周有 Agent 面试，帮我制定复习计划，先准备任务调度这一部分。”

对话中给出简明计划和当前需要的执行批准。已有材料可先处理；缺少岗位要求等关键输入时再问。之后显示“这一部分已交付”“下一部分等待你确认”或已有有效策略下的下一步，不把一次 Run 成功说成整个目标完成。

用户：“先停一下。”明确指向当前 Goal 时走原控制入口；指代不唯一时先问。用户几天后回来，可以在对话中查到原 Goal 的真实进度和成果。

复用 GoalService、GoalRunner、Plan、Checkpoint、Guard 和原批准语义；需要把状态、成果及审批呈现在同一对话，并接通有权对象引用。不得让一个“继续”同时取消 Task、推进 Goal、保存 Memory；保留现有单轮操作约束，复合指令分清目标再处理。

### 场景 E 提醒和有边界的主动跟进

用户：“明天上午九点提醒我检查发布说明。”沿原 Task/Guard 处理，回执写清日期、时区与内容；到时在对话中收到提醒。现有 Scheduler 到期仍可能调用模型，本方案不把它说成已实现零模型固定通知。

用户：“关注这个公开 GitHub 仓库的 main 分支，这周有更新就帮我判断对项目的影响。”Agent 在对话内补齐必要范围，展示简短观察许可摘要。需要自动分析时，再明确展示原 Goal/计划、截止时间、次数及费用上限，由用户完成原 Policy 审批。观察许可和执行许可分别生效，不能把“帮我关注”当成无限授权。

复用现有 GitHub 来源、订阅、Policy/Grant 和事件分派；将准备信息和既有审批控件嵌入对话是待开发入口。初次观察只建基线；无 Policy 时可以显示变化事实，但不得承诺自动分析。原暂停、撤销、busy 不补跑、过期和预算规则保持。

“没有重要变化就安静”是最终产品目标。当前有 commit 变化不等于已判断其对用户重要，当前也没有通用价值判断与通知抑制机制；不得在本次 UI 接线中暗加有费用的筛选 Agent。首批如实显示已观察事实及已有获准分析结果，重要性通知策略另列后续任务。

### 场景 F 出错时知道发生了什么

工作失败时，在原卡片说明“本次没有产出”“已保留此前成果”以及可采取的下一步，技术诊断按需展开。不只显示一个无法理解的红色失败标签，也不在背后重试收费请求。

取消 WorkJob 表示结束这次工作，不能承诺之后从断点继续。进程重启后 queued 保留、running 转 interrupted；重新执行是新的显式请求。Goal 暂停和继续保留原语义，UI 不把两种生命周期混在一起。

### 场景 G 一次交代几件事

用户：“准备面试，也帮我跟进项目。”最终目标是系统能分别组织并协调这些事情。首批尚不支持把一条复合指令自动拆成多项执行，必须在对话里列清“面试准备、项目跟进”两项，并明确它们目前均未启动，再问一次“先处理哪件？”。不能静默只做一项，也不能只生成一份计划就说两件事都已接单。

单项范围明确后，仍由原 Guard 核对当前请求和已有合法草稿/引用。没有对应绑定时不能把旧复合原文截成子命令冒充当前授权，也不能把整段复合需求直接塞给一个只允许单项执行的 Worker。宿主只对实际提交的那一项显示已接单，其余明确标为未启动、待决定；首批这些意向保留在对话中，不冒充持久任务队列。

之后可单列“有界多项分派与依赖”任务，解决一次请求的逐项范围、批准、部分失败、先后关系和逐项回执，复用原业务对象；不提前引入新工作流框架或多 Worker 并行。这是距离最终协调多项工作体验仍需补上的能力。

## 5 推荐的最小实现路线

### 5.1 继续使用现有 Chat 作为协调入口

推荐让原 Chat/Pi 主循环按需请求宿主的受控能力。普通消息仍走 `/chat`，不在每条消息前固定新增一个模型 Router 请求。复用旧 2B 的候选准备和校验；原“路由建议”保留为可选诊断入口，退出日常主输入区。

单纯把全部消息先发 `/work-routes` 再转 `/chat` 会增加延迟和模型调用，也不能解决授权问题；只靠前端关键词判断“后台”则仍要求用户适应机器。两个方案均不推荐。

新能力暂按“工作委派与控制”“工作状态与历史查询”划分，名称由实施任务确定；仿照现有工具，通过公开 Pi SDK 适配，不 Fork SDK、重写 Loop 或引入新 Agent 框架。

### 5.2 用户授权工作内容，系统选择执行方式

这是**需要批准的交互及受控工具权限变更**：用户明确提交一次纯文本交付请求后，允许系统在直接回答与一个纯文本 WorkJob 之间选择，用户不必再说“后台”或点击技术确认按钮。该规则只在用户批准的新模式开启后适用；当前旧接口的显式确认约定不能直接取消。

宿主从当前已鉴权请求取得原文、稳定 requestId 和对象引用；模型提出委派不等于授权。Guard 需检查当前真实请求是要执行这项文字工作，而非讨论、引用旧指令、否定执行或材料中的指令。WorkJobStore.create 自身没有这层自然语言授权，不能直接注册为模型工具。

委派原文冻结，用户身份和 requestId 由宿主提供，模型不得传入任意身份、SQL 或扩大后的 Worker 指令。一次当前请求最多创建一个 Job；同轮不能再借这个入口保存 Memory 或控制 Goal/Task。已提交的接单收据及原 Job 状态优先于模型随后自述，模型收尾失败不能导致重复提交。

后台仍无工具、无 Memory、无网络、无文件写入；只有当前文字在原输入预算内才可委派。缺材料或需要新的能力时，说明缺口并走已有合法入口，不能把“接下工作”当作已授权联网。简单回复零新增 Router HTTP；委派可能产生主 Chat、授权解析及 Worker 的调用，必须实际计数，不能宣传总共只调用一次模型。

### 5.3 去掉主题必选，同时保留真实归属

新增宿主规则：有明确且唯一的当前工作上下文时复用；新提交且没有既有归属的工作，按本次请求建立一个主题，名称只是可改的展示标签，稳定身份仍用 ID。建主题与入队在现有 SQLite 的短事务及原 requestId 去重范围内完成，失败不遗留重复主题，不另造队列。

第一批自动归属只处理本次新 Job 的 threadId，不自动重排历史数据、不按主题名字合并、不自动添加旧 Goal/Task/Memory 的 work_links；这些关系仍经原明确关联入口。后续若需要系统推断关联，要明确新增来源标记和纠正方式，不能把 source=user 写成假的用户决定。

主题满额、归档、对象失效或归属歧义在对话里给出具体原因及可执行选择，不恢复为永久必填下拉框。

### 5.4 展示与“Agent 真正知道”分别接通

前端卡片引用原 Job/Goal/Run；后端只在现有 Web 请求/关系记录中补充必要的原请求与对象引用。若需迁移，只增加关系元数据，不复制成果正文、创建第二套状态或持久会话系统。最小字段与迁移方案在实现前的任务卡中冻结。

自然指代通过当前对话中可信对象引用与有界候选定位。不能仅凭最新完成时间，把后台晚到的另一个结果视作用户的“刚才”；不明确就询问。客户端提供的对象引用仍须按当前身份校验，命中来源仅表示可读，不表示可执行。

Recall 继续默认不读长期 Memory。对话工具输出有来源、有截断标识的低信任资料；“旧材料里写了同意”不能变成新授权。优先使用现有公开 context 临时投影方式，保存必要引用和执行收据，不持久灌入所有旧正文。

### 5.5 审批嵌入对话，许可语义保持

Goal 的计划/批准、文件预览、观察许可和自动执行 Policy 仍由原服务校验。对话负责准备用户可读摘要、展示既有控件和反馈结果，不让模型代点确认。原文缺少关键字段才补问；已有效授权范围内不因为换了 UI 再问一次。

“开始观察”和“批准有限分析”是两项不同授权，可以在同一张简明卡片里分别表达。预览不能自动记录为已批准，普通“好”也不能确认多个未明确绑定的请求。第一批不为 Task 提醒、取消工作等已有清晰授权行为增加一律二次确认。

## 6 实施拆分与预计文件

方案批准后再开始，第一批至少完成 C1+C2；仅交付把按钮藏起来的 C1 不算目标体验验收通过。各任务由 Worker 实现，独立 Reviewer 对真实 diff、输入输出和测试证据审查，最多三轮。

| 任务 | 可独立验收的交付 | 预计涉及文件 |
| --- | --- | --- |
| C1 对话承载已有工作 | 已有 Job/Goal 的真实进度和成果出现在对话里，刷新去重、失败可理解、原审批无变化 | `web/src/main.tsx`、`chat-timeline.ts`、`work-jobs.tsx`、现有样式；`src/web-ui-types.ts`、`web-ui-channel.ts`、必要时 `web-ui-store.ts`；对应 Web/时间线测试 |

## 7 怎么验收

| 验收场景 | 通过标准 |
| --- | --- |
| 初次进入、没有主题 | 用户能直接提交请求；简单任务直接返回，后台分支不要求提前创建主题或选择模式 |
| 当前三条待办原例 | 只整理文字；无 Job/Goal/Task/Memory/主题新增，零额外 Router 请求 |
| 较长完整材料 | 同一次请求至多一个工作；接单、状态、成果在对话内可见，不靠用户找收件箱 |
| 一句话包含两项独立工作 | 首批不自动拆分执行；两项均被识别并明确尚未启动，只问一次优先级；后来单项真正提交才标已接单，另一项不丢失、不假称已排队 |
| 工作期间继续聊天 | 慢模拟 Worker 未结束时 Chat 已正常回答；第二个后台工作仍串行，不能用很快完成的任务冒充重叠验证 |
| 反馈修改与找回 | 显示成果后自然追问，实际模型输入使用正确、有权、有效的结果；另一主题的晚到结果不替换引用 |
| 歧义与业务归属 | 两个相似目标先澄清；错 ID、其他渠道、归档或已删除对象不可查询/执行；无越权关系写入 |
| 真实进度 | Job lifecycle、Goal checkpoint 和原库一致；Run 成功不冒充 Goal 完成；没有编造步骤/百分比 |
| 取消、错误、断网 | queued/running 取消正确；迟到结果不覆盖终态；同 requestId 重试不重复提交；通知失败能读成果、不重跑模型 |
| 刷新与进程重启 | 原卡片/结果可恢复；queued 与 interrupted 沿原规则；前端重载不补执行、不替用户批准 |
| 历史内容与权限 | 旧成果中的“确认/保存/联网”不执行；Recall 默认无长期 Memory 读取、无审批 ACK；非工作请求不被委派 |
| 持续授权与事件 | 原观察和执行许可分别核对；过期、撤销、预算、busy 均沿原规则；新事件不会凭主题关联获得执行权 |
| 桌面与窄屏可用性 | 主要使用流程始终一个输入框；无需学习 WorkJob/Run/Router；长结果可读，必要控制能找到 |

验证顺序：临时 SQLite 和 localhost 模型/来源桩验证机制 → typecheck、后端/前端 build、全量测试及受影响回归 → 独立 Reviewer 审查 → 用户在隔离实例做有限真实使用验收。每轮记录任务是否完成、人工补充/纠正次数、必要审批次数、模型/网络请求数、耗时与已知费用。模拟 API、真实浏览器、真实模型和实际手机分别记载。

真实验收以“我只说需求，能拿到并继续使用成果”为标准。用户若仍需被指导先选哪种模式、去哪个隐藏区域拿结果，基本体验不通过。必要的授权和真实歧义澄清不算多余操作；为验证内部执行器强迫用户选模式算多余操作。

## 8 仍需批准的决策与暂不包含的能力

待批准的核心方案是：保留主 Chat 为协调入口；允许受控纯文本委派而不要求用户说技术模式；允许宿主为本次新工作建立主题元数据；将有权状态/Recall 接为按需只读工具；把既有审批控件嵌入对话。前三项改变当前显式按钮提交边界，后两项增加 Chat 能力接线，不能把“简化 UI”当作已经获得执行授权。

这轮不启动上述实现，也不发布、合并、开正式开关或发起收费测试。下一次应先批准产品方案及首批 C1+C2 的具体范围，再按同一流程推进；C3/C4可以在用户批准的连续开发范围内继续，不自动推定本轮已批准。

以下属于最终目标的后续缺口，不塞进这次界面任务：后台通用联网研究、多 Worker 并行、跨渠道身份统一、电脑离线后的常驻服务、任意连接器、自动长期记忆、通用重要性判断及低打扰通知、可靠外部推送。已有固定 GitHub 观察和有限执行不等于这些能力全部完成。

同一请求的有界多项分派与依赖也需后续单列；它与多个后台 Worker 并行不是一回事，可以继续复用串行执行。C1—C4 接通已存在的能力，不等于已经完成原规划中全部多事项自主协调。

当前普通 Chat 原文复测成功依据用户反馈；显式后台 Work 的真实闭环尚未完成，已有测试总数不能替代它。原真实失败与未执行项继续保留。本轮仅源码与文档审查，不重跑工程测试或收费模型；文档链接、差异和已有代码保护另行核验。
