日期：2026-11-02。状态：**用户已于2026-11-02明确批准 T1—T6 隔离开发与离线验证**。Git 发布、正式启用、正式数据迁移和付费测试仍需另行授权。本任务书落实[架构复盘](super-agent-alignment-review.md)，优先完成自动承接、隔离执行、原工作续接和同一对话交付。旧[交互方案](chat-first-interaction-plan.md)的界面原则保留，旧 C1—C4 顺序不再作为实施依据。

## 1 交付目标与范围

用户在一个对话框里连续交代面试提纲、项目周报、文章修改三件事，不选择主题、对象或后台模式。系统自动组织为独立工作；用户可以问进度、补充要求、修改成果、停止工作，系统找到正确对象并报告真实状态。后台先串行执行，主对话能继续接收消息。

本批工作能力限定为**本机 Web 内、用户提供文字和明确引用的已有纯文本成果**。同一消息最多承接三项独立纯文本工作；既有 Task/Goal/Memory/文件/联网能力保留原入口和批准语义，不扩展成批量执行。Goal 的查询、显式控制及既有获准事件继续走原服务，不把 WorkJob 包装成长期 Goal。

Router/Worker 在本批接成完整用户流程；事件部分统一呈现已有工作完成和既有 Goal 事件事实；Recall 提供可信定位与最小成果续接。不会新建通用事件总线或任意事件自动规划器。后台联网、文件工具、Worker 并行、飞书身份贯通、自动长期 Memory、通用任务依赖图、常驻部署和可靠外部推送不在本批。

## 3 用户可见行为

| 用户输入或事件 | 应有行为 | 验收重点 |
| --- | --- | --- |
| 根据所附文字准备面试提纲 | 自动找到或建立工作，先回执，再交付成果 | 不需预建主题或点击后台按钮 |
| 面试运行中再发项目周报 | 第二项可靠接收，后台按原顺序执行 | 接收与模型开始执行分开，不伪报运行中 |
| 面试那份重点讲调度 | 定位面试工作；已有成果则创建后继执行，运行中则登记下一版补充 | 说清已收到、待采纳、已采纳；不修改在途输入 |
| 再简短一点 | 有唯一可信指向时续接；有两个合理对象时用名称问一句 | 晚到的其他工作通知不能抢走指代 |
| 停下面试那件 | 取消该工作的可取消 Job，并撤销尚未消费的后继许可 | 不影响周报，不承诺从取消位置恢复 |
| 同一句给出三项文字整理请求 | 保存三项身份和逐项回执，按授权分别入队 | 不一律要求用户只选一项，不丢弃后两项 |
| 工作完成、失败或已获准 Goal 事件更新 | 在同一对话给真实成果、状态或需要用户决定的问题 | 通知不额外触发模型，不自动产生新许可 |

“收到”只表示持久接收；“排队”表示执行请求已创建；“处理中”来自真实运行状态；“完成”来自已提交成果。不得用模型措辞推断这些状态。用户可以展开原工作台查看详情，日常输入框只保留输入与发送。

## 4 协调与授权契约

### 4.1 总管入口

复用主 Chat 和 Pi 公开工具机制，新增一个仅新模式可见的受控 `work_manage` 工具，参考现有无参数 `goal_manage`：主模型提出管理工作意图，宿主根据**当前完整原话**、可信工作引用和真实存储决定执行。独立解析器不接受主模型生成的指令正文或授权；读取历史、Memory、网页或旧成果不能产生新权限。

总管负责区分普通交流、新文字工作、原工作补充、查询、取消和澄清。明确的独立交付及持续修改应进入 Worker；短问答可以直接回复。验收用场景而非固定字数阈值判断是否正确委派。主模型漏调用工具必须如实暴露在语义验收中，不能以宽泛关键词兜底制造已承接记录。

宿主解析入口一次校验 Schema、原文证据及候选范围，后续传递类型化值。证据片段必须能在原话中定位；同文本多处出现且影响范围时澄清，不让模型编造字符偏移。共享约束与每项正文分开绑定，Worker 不能收到其他子项正文。

### 4.2 一次操作与多项文字工作

新 `text_work_batch` 是一个有界宿主操作：最多三项，全部保留父请求及稳定子项身份，各项只能使用该用户已有权限内的文字输入。宿主逐项检查目标、来源和执行范围，再一次消费现有 Frame；不能为拆出的子句新开多个 Guard Frame。

纯文本批次在短事务内一起保存决策、子项及当时可创建的 Job。结构、来源或权限校验失败则整批不提交；若只是某个合法子项的目标或材料有歧义，该项保存为待澄清，其余明确且独立的子项仍可提交，不能要求用户重述全部。事务失败全部回滚；执行开始后各 Job 可以独立成功或失败，按项报告，不重跑成功项。重复工具调用、重复提交或刷新只能回读同一收据。

超过三项或存在不能独立执行的先后依赖时，保留完整原消息并说明未启动范围，不截成前三项；先澄清分批或转入既有 Goal 流程。本批不实现跨 Job 依赖图。

不修改旧 Task/Goal/Memory/文件操作的单轮约束。同轮新批次与旧业务写操作不能重复消费。若一条消息同时要求文字处理和创建提醒、Goal 或保存记忆，保存完整需求并说明需要分开的授权事项；本批不自动执行这种混合写批次。普通的“不联网、不建 Goal、不保存记忆”是文字工作的限制，不应被误判为另有写操作。

纯文本明确请求即为该项有限执行意图，不增加每项必点确认。缺范围、歧义、超预算或新增权限时才澄清。旧 `suggest/confirm` API 保持原意，不能后台调用 confirm 来假装用户点过确认。

### 4.3 补充与后继执行

工作身份与一次执行分开：文字工作的稳定引用为首个 Job 的 ID，后续 Job 挂同一根引用；Goal 仍用原 goalId。WorkThread 仅组织工作，主题、任务类型和 Pi Session 均不能充当执行身份。

已完成成果的修改创建新 Job，原 Job/Run 不变。输入由宿主选取当前用户修改、该工作目标与有效约束、指定已提交成果及出处，冻结后执行。不得读同主题全部历史作为上下文。指定旧版本且有歧义时澄清，不能自动取最新版本替代用户指定版本。

运行中补充先持久登记。建议首版语义：**当前一轮结束后，将领取前收到的补充合并到至多一个后继执行**；必须有一条明确要求修改/继续的当前请求作为这次有限许可，例如指向面试工作的“重点讲调度”可以是修改意图，不要求用户学习固定命令。纯补充资料但没有要求执行的输入只保存，等待用户指示。每条补充显示所属工作及消费它的 Job，不能把“已接收”说成“已应用”。

后继领取时才冻结本轮补充集合，之后收到的新修改属于下一轮。第一次执行失败、中断、被取消，或所需成果不完整时，待续输入标记需要用户处理，不自动产生新模型请求。终止工作撤销未消费许可；已经取消的 Job 迟到结果仍不能成功提交。不增加在途模型插话、自动重试或无限自推进。

为避免暗改已经冻结的排队 Job，待续阶段只保存子项/补充收据。原 WorkRunner 取得执行门且就绪检查通过后，同一短事务聚合输入、创建并领取后继 Job/Run、消费有限许可。领取后的补充需下一次明确许可。后继候选按许可到达顺序与原 queued Job 比较，仍尊重到期 Task、就绪 Goal 优先；不另建调度器或让后继工作插队。

明确 Goal 续接继续使用 GoalService/Guard 的版本与计划批准；不把 Job 反馈协议注入 GoalRunner。运行中或受主动 Policy 管理的 Goal 不接受新的自动旁路续段，保留原暂停、交接和继续条件。

## 5 数据与上下文边界

### 5.1 可靠接收

当前 [WebUiStore](../../src/web-ui-store.ts) 的 `web_ui_chats.runId` 非空，accept 即创建 running Run；[WebUiChannel](../../src/web-ui-channel.ts) 忙时拒绝，不能只删 busy 判断。

建议增量迁移原接收表，使新模式的消息先落盘 `queued`、runId 可空，领取时原子创建 Run。增加接收时间以排序；旧行关联、正文、mode 和 Run 原样保留。迁移脚本只能在临时旧版 SQLite 上验证，正式实例迁移不包含在开发授权中。队列生命周期属于消息接收，不复制 Job 或 Goal 状态。

同一 owner/requestId 同原文返回旧收据，冲突拒绝，幂等回读先于容量检查。新模式最多等待八条未领取消息，满时明确未接收且保留输入草稿，不静默丢弃或自动重发。沿现有 Chat 长度与 HTTP 请求体上限接收，超过 Worker 的 14 KiB 组装上限时明确不能委派，不静默裁剪。未领取消息可从其收据撤回，宿主按 requestId 校验并取消，不调用模型；已领取的不伪报已撤回。

单次 Chat 仍串行；后台 Worker 执行不占接收门。foreground 只包围当前处理回合，不因等待队列非空一直占用后台门。队列内只有 queued 消息跨重启可领取，已领取 Run 保持原 interrupted、不自动重放。模型响应失败但 Job 已提交时，回读已提交子项，不能因 Chat 失败再提交一批。

### 5.2 最少持久关系

| 位置 | 拟增加的最小信息 | 不承担的职责 |
| --- | --- | --- |
| 原 `web_ui_chats` | 接收状态、createdAt、可空 runId；协调模式标记 | 不保存 Job 执行状态或另起会话数据库 |
| 新 `web_request_items` | itemId、父 requestId/owner、序号、原文范围、决策及有限许可、目标引用、待消费补充关系、consumedByJobId | 不存旧成果正文，不成为第二套 Task/Goal 引擎 |
| 原 `work_jobs` | rootJobId、previousJobId、sourceItemId、冻结输入引用及 Hash | 结果和用量继续读 Run，终态不重开 |
| 原 Web/Run 审计 | 用户请求到子项、Job/Goal、成果的因果引用；当时收据 | 通知入箱不等于用户已读或审批 |

子项 ID 由宿主创建并持久化，作为新 Job 的幂等 requestId；不改变 `UNIQUE(owner,channel,requestId)` 的意义。旧显式 Job 的根引用按自身 ID 解释，空的新字段不能改变旧输入与执行路径。只新增这一张子项表，不另建通用工作实体或 Session 注册表。

同一工作领取前的补充可共享一次明确后继许可，消费与新 Job 创建同事务。字段名及约束在 T1 内按此数据职责定稿；若发现必须另建执行状态机、修改旧生命周期或引入跨库事务，停止并报告，不由 Worker 自行扩展。

主题可以由宿主为新工作创建或复用明确唯一主题，命名基于本次目标；不要求用户先管理主题。归属仍绑定本机 Web，自动决定记为宿主来源；不伪造 `work_links.source=user`，不自动关联或合并既有 Goal/Task/Memory。

### 5.3 模型看到什么

总管当前回合可以看到当前原话；目标是**历史工作全文不跨回合反复累积**，不承诺总管从未看过当前长材料。通过 Pi 公开 `context` 返回投影，给总管保留有限工作目录、当前指向、当时收据和必要短摘要。原始 Session 与 Web 原文不删除、不重写；Guard 始终拿完整当前原文。快照先复用目标名称、真实元数据、已有 Goal progressSummary 和标明省略的短节选，不为压缩额外调用模型。

通过公开宿主标记绑定请求与回合边界，不按原文字符串猜测哪一回合可裁剪。旧 Session 没有这些标记时，从新模式第一次请求建立明确边界：此前工作正文不自动整段带入，改用业务索引；普通交流最多保留最近两轮且总计 4 KiB，无法可靠区分的旧混合回合只保留来源引用，按需找回。界面仍保留原历史；这种模型输入变化只在新开关开启后发生，旧模式不变。

必须保留当前回合合法 toolCall/toolResult 配对及旧审批引用所需的宿主状态。投影不得覆盖 Memory/网页的既有低信任处理，也不得用历史批准作为新权限。先用临时 Session 验证公开 API 的实际效果，不修改 Pi 内部数组或 SDK 源码。

Worker 继续使用临时独立 Session、零工具和原一次 provider 请求。宿主按需读取该工作已提交纯文本成果，验证 owner/channel、对象、状态、版本或 Hash；本文不新增 Memory 正文入口。每次续接最多一个明确主前序成果，保留必要约束；跨工作成果合并不自动开放。Goal 成果必须为原服务认可的有效 committed Checkpoint，不能因技术 Run 成功就替代业务提交判断。

旧成果全文仍在原 Run。现有 Recall 返回的是有界节选，不能冒称已加载全文；需要修改整个成果时，由宿主按同一来源/权限规则冻结所需正文。冻结输入保存来源引用及 Hash，缺失、变化或预算不足时不换用另一份成果，也不静默按节选完成全文改写。候选目录沿用现有最多二十个对象、8 KiB 元数据的限制，查不到唯一目标时澄清或按明确名称缩小，不猜 ID。

新组装输入继续受原 14 KiB 输入、32 KiB 实际请求体、4096 输出 token 和超时约束；总管及辅助解析共用每轮八次模型 HTTP 上限，不能漏记新解析调用。保留用户否定、范围和格式约束；不能静默截断关键材料后声称完整改写。超过范围则说明缺口并让用户缩小，工具不能放宽预算。

## 6 任务拆分与依赖

以下 T1—T6 是同一已界定交付目标内的小任务。必须整批验收后，才称为“总管最小可用流程”；中间模块通过不对用户宣告目标完成。

### T1 接收与工作引用基础

交付：迁移与类型、可靠消息接收/领取、子项表、Job 根引用和前序关系、默认关闭的 `WORK_COORDINATOR_ENABLED`。仅本机 Web 组装，依赖现有 WorkThread、WorkJob、Recall；不要求开启旧路由建议 UI。开关关闭走旧 Chat/Job 路径，已创建记录保留但不领取新协调消息或后继输入。

预计文件：`src/web-ui-store.ts`、`src/web-ui-types.ts`、`src/web-ui-channel.ts`、`src/web-ui-server.ts`、`src/work-job-types.ts`、`src/work-job-store.ts`、`src/sqlite-store.ts`、`src/config.ts`、`src/main.ts`；按需新增一个 `src/work-coordinator-store.ts` 管理子项关系。不为一次性迁移另建框架。

验收：临时旧库迁移前后旧记录一致；queued 尚无 Run；领取原子；重复/冲突请求；八条满额行为；真正子进程重启只处理 queued，claimed 不重放；新开关关闭旧行为不变。此时尚无自动委派，不独立提供真实使用测试。

### T2 自动承接与一次有限批次

依赖 T1。交付：`work_manage`、当前原话隔离解析、纯文本批次 Guard、自动主题组织、单消息一至三项逐项收据；查询与取消绑定真实对象。旧显式 suggest/confirm 保持兼容。

预计文件：`src/work-router.ts`、`src/operation-guard.ts`、`src/pi-executor.ts`、`src/contracts.ts`、`src/work-thread-service.ts`、T1 存储与组装；按需新增 `src/work-tools.ts` 和一个有明确职责的协调服务。沿用既有预算、错误、取消和审计，不重写 Guard。

验收：脚本化模型真正调用新工具；三子项单 Frame、一次消费、三独立 Job；重复工具无重复 Job；否定、引用、假设、越权对象、伪造候选与混合写请求按契约处理；旧 Task/Goal/Memory 工具不能再消费本轮权限。保留已有合法 none Chat 修复及回归。

### T3 原工作定位与隔离续接

依赖 T2。交付：可信工作焦点、按名称/引用定位、最小 Recall、前序成果输入、运行中补充及一次后继许可。后台收件箱通知不能自动改变用户当前所指的工作；存在合理歧义就澄清名称。

预计文件：`src/work-recall.ts`、`src/work-runner.ts`、`src/work-job-store.ts`、协调服务/子项存储、`src/contracts.ts`。Goal 控制复用原服务；只有确实必要的接线才触及 Goal 代码，不改其 Runner/Policy 语义。

验收：同一主题下两项工作也不串材料；后继请求包含正确原成果及补充；在途输入不变，领取前补充共同消费一次，领取后补充归下一轮；取消/中断/失败不自动后继；恢复能解释哪些补充已采纳。捕获模型入站 payload，而不是只验界面标签。

### T4 总管上下文投影

依赖 T2、T3 的稳定引用。交付：新模式总管职责提示与公开 context 投影，历史工作全文从后续 provider 请求中排除；当前原文与 Guard、旧审批引用分别保留。直接对复杂工作长篇作答而未委派的情形纳入失败样例。

预计文件：`src/pi-executor.ts`、`src/contracts.ts`、协调服务与有限引用持久化；不改 Session 文件格式、SDK 或旧模式的上下文路径。

验收：三份带独有标记的材料交错两轮，分别检查总管和 Worker 实际 HTTP payload；总管后续回合不累积三份全文，Worker 不带其他工作或主 Chat 历史；临时 Session 重开仍能定位；当前工具协议、Memory 低信任投影、Goal/文件批准引用仍有效。若公开 SDK 无法支持必要投影，先报告限制，不改内部 Loop。

### T5 一个对话入口与统一交付

依赖 T1—T4。交付：新模式主输入去掉主题/模式/对象必选项；接收期间可继续输入；同一时间线显示请求子项、真实进度、结果、澄清和失败。工作详情复用现有工作台，保留必要取消入口。

预计文件：`web/src/main.tsx`、`web/src/chat-timeline.ts`、`web/src/work-jobs.tsx`、必要的样式、`src/web-ui-types.ts`、`src/web-ui-channel.ts`。Goal/文件完整展示与审批 ACK 仍用原明示流程，不能因卡片出现就自动授权。

工作完成优先投影原 Job/Run；即使通知投递失败，已关联成果仍可查看，不因缺通知重新执行。通过现有状态回调与查询汇总用户输入、Job 完成和获准 Goal 事件，不加通用消息总线或每事件模型唤醒。已有 GitHub 观察/Policy 仅用模拟来源验兼容，不新建或扩大许可。

验收：真实浏览器桌面与 390px 窄屏完成三项交错操作；输入不丢、结果不重复、刷新引用仍正确；失败可见，技术 ID 按需查看；Goal 事件与人工工作不互相冒用许可。窄屏不能写成实际手机验证。

### T6 整体验收与交付

依赖 T1—T5。Worker 运行适用定向测试及 `npm run typecheck`、`npm run build`、`npm run web:build`、`TMPDIR=/private/tmp npm test`，记录最终同一源码版本结果。独立 Reviewer 核对原需求、完整 diff 和日志，并独立复验关键跨模块反例与用户流程，不只审 Worker 总结。

预计文件：现有相关测试及必要的新 `tests/work-coordinator*.test.ts`、`tests/web-chat-timeline.test.ts`，新增评估记录；更新 `docs/STATE.md`、获批准且实际实现的 `docs/PROJECT.md` 和运行说明 `README.md`。不提前把任务书中的建议写成已确定或已上线架构。

交付可审查 diff、文件目的、迁移/恢复/权限/浏览器证据和未验项。真实模型、实际手机、长时间运行另列未验；本批完成后再提出一份用户手动真实试用清单及明确费用范围，不自动发请求。Git 提交、推送、PR、合并和运行实例切换均等待另行明确授权。

## 7 最终验收矩阵

| 编号 | 必须实际验证的场景 | 通过标准 |
| --- | --- | --- |
| A1 | 连续三条不同工作及一句三项，两组分开 | 每组全部独立承接，无人工模式选择；不把三条测试冒充复合请求 |
| A2 | 用受控屏障让 A 保持运行，再提交 B 和普通问题 | B 在 A 结束前已持久接收；普通问题可处理，记录实际接收/响应延迟 |
| A3 | A/B 同主题、各两轮、C 通知晚到 | 后续输入和旧成果归属正确；入站 payload 无另一工作标记 |
| A4 | A 运行中两条补充，领取前后分别到达 | 已收到/已采纳可核对；一份有限许可只生成一个后继 Job；冻结输入不变 |
| A5 | 合法操作、引用中的伪指令、否定/假设、越权ID、重复工具/消息 | 预期操作执行一次；无授权操作零执行；不能用旧成果绕 Guard |
| A6 | queued/claimed/已建Job但Chat未finish三个点杀进程 | 未执行队列可恢复；已执行不重放；已承接Job可回读；补充许可不重复消费 |
| A7 | 取消、失败、中断、通知失败、来源缺失/超预算 | 不伪报成功，不自动收费重跑；成功成果仍可按原引用读取 |
| A8 | 旧库、新开关关闭、旧 Task/Goal/Memory/Web、已获准事件 | 原身份/正文/授权与执行语义不变；不访问其他渠道数据 |
| A9 | 浏览器全流程、刷新、窄屏 | 同一对话能交代、查进度、补充、停止、收成果；详情只作辅助 |
| A10 | 模拟模型与后续真实语义验证分开 | 离线覆盖全部确定性契约；真实路由正确率、质量、请求数/费用如实待验 |

离线验收使用临时 SQLite、临时 Session、虚构材料及 localhost 假模型/来源。每组记录请求数、人工澄清/选择次数、真实状态及错误路径。多一层总管不保证更便宜或更快，实际比较不能省略协调请求。

## 8 需要用户批准的具体范围

建议一次批准 T1—T6 的**隔离开发与离线验证**，包括：本地独立分支、上述接收表迁移代码与临时库验证；新增仅纯文本的受控委派批次；自动主题元数据；按原成果重建独立执行上下文；明确请求下的一次后继执行与领取前补充合并；总管历史投影及对话入口调整。

这些涉及当前只支持显式后台提交的架构与宿主能力变化，因此按 AGENTS 的确认规则在实施前请用户明确批准。批准本任务书不批准正式数据迁移、运行实例切换、外部权限扩张、付费语义测试或 Git 远端发布。后续在此范围内可按任务顺序自主执行和修复；遇到重大不同方案、重要设计分歧或三轮审查未通过时暂停。
