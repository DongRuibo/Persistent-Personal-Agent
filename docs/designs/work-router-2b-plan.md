## 建议的交互范围

首批在同一 Web 输入区提供一个可选的“路由建议”入口，保留“发送聊天”和“后台处理”。自然语言分类和主题建议在该入口内完成；不为每条普通聊天新增一次分类请求。该交互选择是本任务书的建议，须随 2B 任务范围确认，不能描述为用户已经批准。

| 当前输入或上下文 | 2B 行为 | 执行边界 |
| --- | --- | --- |
| 明确选择主题和后台处理 | 继续现有 2A 确定性入口 | 零 Router 模型调用，创建后才显示排队收据 |
| 请求路由建议，输入“整理以下面试题……” | 建议一次性纯文本工作及一个主题，展示本次原文 | 用户确认后调用现有 WorkJob 创建；不把建议说成已排队 |
| “10分钟后提醒我面试” | 建议交回现有聊天入口处理提醒 | 原文不改写，Task/Guard 解析时间及授权；Router 不创建 Task |
| “继续准备面试的长期计划” | 展示有权访问的 Goal 候选及原入口 | 原 Goal/Guard 判断目标和执行权；Router 不生成 Grant 或假造已确认引用 |
| “上次那个项目”而可见候选不唯一 | 展示有界候选，要求用户选择 | 不按最高相似分数自动认领；不扫描历史做 Chain of Recall |
| 要求写文件、联网、跨渠道或没有提供原文材料 | 如实说明当前建议入口的能力边界，并允许回到原聊天 | 不把无工具 Worker 包装成文件生成或联网 Worker |

确认仅表示用户同意当前展示的主题和本次纯文本工作；不扩大文件、网络、Shell、Memory 或外部系统权限。需要提醒/Goal 操作时，后续请求仍由原服务处理。用户编辑输入、切换主题或撤销建议后，旧建议失效。

## 数据与模块边界

1. **确定性定位优先。** 用户明确选择的主题、明确对象 ID，以及当前界面可证明的选择用于定位。显式冲突、不可见 ID 和归档主题不得被模型静默替换。只确定主题不等于已经确定执行意图。
2. **模型只输出建议。** 最小结果类型为 `chat`、`existing_task`、`existing_goal`、`work`、`clarify`；附带允许候选中的 ID、简短理由或澄清问题。对象正文、权限、任意工具名和任意 SQL 不属于结果协议。结果在模型适配入口校验一次，再传入已定类型。
3. **候选由宿主构建。** 仅当前 Web 身份；复用 WorkThreadService 和原对象归属查询，读取主题/Goal/Task 元数据。模型不得自行扩大搜索范围或提供新 ID。当前选择优先；建议上限为 20 个主题、所选主题最多 20 个 Goal/Task 元数据项；超过时让用户缩小范围，不把截断集合说成全库不存在。
4. **不读取 Memory 正文或 Session。** 现有 `WorkThreadService.detail()` 遇到 Memory 关联会调用 `listForHost()` 并读取 Markdown；因此不能为了拿 Goal/Task 就无条件对全部主题调用 detail。应对现有服务做局部的种类过滤查询，复用原归属判断；不新增第二套权限规则，不触发 Memory 扫描。现有公开 detail 行为保持。
5. **复用当前模型与 SDK 适配。** `ModelRuntime.completeSimple` 已在 `src/pi-executor.ts` 用于隔离意图解析，可复用其配置、取消和 observer 方式。新建议协议与 OperationGuard 的授权解析分开，不把路由结果塞进 Guard 当作用户意图证明。Pi 类型仍集中在现有适配层。
6. **原业务事实源不变。** `WorkJobStore` 负责创建、去重、取消、恢复；`WorkRunner` 负责执行；Goal/Task/Memory 保持原服务与 Guard。不增加 Router Runner、任务框架、通用事件总线或新数据库。
7. **建议不是业务执行。** 建议请求及实际模型用量复用原 Run / events / model_calls。可在已有 Web 请求记录上区分“建议”与“聊天”，让刷新后显示已完成建议或中断状态；不得将建议 Run 当作 WorkJob 成功结果或提交收据。Worker 在任务 1 先确认最小持久标记方案，避免新增建议表。
8. **幂等与恢复。** 同一请求 ID 的模式、原文和选择上下文必须匹配；不同输入冲突拒绝。重复提交已存在请求只读回结果，重启后不自动补调模型。确认后台工作继续复用 2A requestId 去重；同一建议的确认重试不能生成两个 Job。待确认 UI 状态不继承执行权限，恢复后重新核对主题/对象的当前访问权和状态。

## 默认开关与请求预算

- 建议增加独立 `WORK_ROUTING_ENABLED=false`，依赖本机 Web、WorkThread 和 WorkJob 已开启；缺失依赖时明确拒绝启用。名称由 Worker 按现有风格落实，无需为名称另建抽象。
- 关闭后不注册建议入口、不暴露建议 UI、不请求 Router 模型；旧 Chat、Task、Goal、Memory、2A 显式后台行为不变。
- 每次显式建议请求最多一次模型 HTTP，无隐式重试、工具、Memory 查询改写或备用模型。已有确定性入口为零次。
- 计划上限：用户文字 14 KiB UTF-8，候选元数据 8 KiB，实际模型 payload 32 KiB，输出 512 token，10 秒超时。预算不足提示缩小范围，不静默丢失原文，不拆成多次请求。
- 解析失败、截断、模型错误、超时或取消：返回明确的“未形成建议/已中断”，不创建工作、不自动转交普通聊天；用户可以另行选择原入口。
- 需要原 Chat/Guard 的操作，其后续请求仍遵循原有预算。必须分别报告 Router 请求与后续 Chat/Guard 请求；不能把“Router 最多一次”说成整个用户操作只有一次调用。
- 本阶段开发和自动化只用临时 SQLite、合成数据及本机模拟端点；真实模型试验的请求数、费用、模型与停止条件需另行批准，不沿用旧阶段额度。

## Worker 任务卡与验收顺序

同一 Worker 串行完成以下四项，每项冻结交付后由独立 Sol / High Reviewer 审查。Reviewer 只读；存在阻断项回交同一 Worker；单任务正式审查最多三轮，第三轮仍阻断则暂停。Planner 不承担主要业务代码写入。

| 任务 | 工作与预计文件 | 独立验收条件 |
| --- | --- | --- |
| B1：冻结契约和确定性定位 | 阅读现有路由与授权；在 `src/work-router.ts` 增量定义建议协议，按需增加 `src/work-route-types.ts`；局部扩展 `src/work-thread-service.ts` 的元数据查询；编写路由夹具 | 主题/对象存在与归属正确；冲突或多候选澄清；关闭状态和原显式路由不变；无模型请求、无 Memory 正文读取；说明建议记录与请求去重的最小接线方案 |
| B2：有界模型建议 | `src/pi-executor.ts` 的公开 SDK 适配、必要 `src/contracts.ts` 类型、`src/work-router.ts`、`src/config.ts` / `src/main.ts` 接线 | 模拟合法/畸形/越界 ID、否定/引用/假设输入、超时、截断、取消和禁止工具；实际 HTTP ≤1，0业务副作用；模型结果不能产生授权 |
| B3：Web 建议与确认 | `src/web-ui-channel.ts` / `src/web-ui-server.ts` / `src/web-ui-types.ts`，必要的 `src/web-ui-store.ts` 请求区分；`web/src/main.tsx` 及最小样式 | 登录/Origin/CSRF/归属沿用；建议→选择/修改→确认→真实 Job 收据→继续聊天→结果；刷新、重复确认和断线重试不重复执行；失效建议不误提交；Goal/Task 返回原授权入口 |

## 必须保留的反例与证据口径

- “暂停那个学习计划”但有多个匹配或泛称不确定：不得擅选另一对象，也不能报告已暂停；沿用原 Goal 授权流程。旧真实模型暂停失败仍单独保留，Router 的离线通过不能覆盖它。
- 用户只看见建议或执行回执，不等于已创建/完成工作；只有原存储提交成功后展示对应事实。历史主模型误读收据的样例加入回归，但不把固定回放当成新真实模型语义验收。
- 引用“帮我取消/保存”、否定、假设、跨主题提示注入：不能因路由建议触发后台工作、Task/Goal 控制或 Memory 保存。
- 已选主题与文字中的明确对象冲突、候选对象后续归档/删除/权限失效：说明冲突并重新选择；不能静默切换目标。
- 路由建议请求在途时用户编辑输入、撤销、刷新或关闭服务：迟到建议不能覆盖当前输入或自动发起工作；已提交 WorkJob 的恢复语义仍由 2A 管理。
- 离线指标分开记录：固定语料的类型/主题命中率、歧义澄清正确率、越权/误执行数量、每条路径的 Router 与整体模型请求数。固定模拟输出只证明接线和约束，不证明真实模型路由准确率。
- 不声称已完成历史召回准确率验收；读取关联原始结果并给出处属于第四阶段。
