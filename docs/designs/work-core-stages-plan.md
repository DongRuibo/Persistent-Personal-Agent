## 阶段顺序与可验收任务

### 2B：路由建议与澄清

以已有独立审查通过的 [2B 任务书](work-router-2b-plan.md) 为实现方案：同一 Web 输入区可选“路由建议”，宿主确定性定位优先，模型只给建议，歧义先澄清，用户确认后才由既有入口执行。普通 Chat 不增加分类请求，不改写原话、Guard 引用或授权。

1. **B1 契约与定位：** 类型/候选与确定性定位，复用 WorkThread 的 Goal/Task 归属查询，零 Memory 正文读取；冻结建议请求的模式、上下文、审计和稳定确认 ID 方案。只做本任务必要实现，不提前接模型/UI。
2. **B2 模型建议：** 复用 Pi 公开 SDK 宿主适配，有界单请求、实际 payload/输入/输出与取消限制；模拟错误和越权结果拒绝，仍零业务副作用。
3. **B3 Web 闭环：** 建议、澄清、确认、实际 WorkJob 收据与继续聊天，幂等与重启不重放；Task/Goal 交回原授权入口。
4. **B4 阶段验收：** typecheck、两端构建、全量测试和隔离桌面/390px浏览器；离线机制与真实语义未验证明确分开。

### 阶段 3：统一事件入口与显式订阅

先读取实际 GitHubObserver、GoalPolicyStore、Policy/Grant、Web 身份和主题实现，再冻结最小数据模型。第一批仅复用已有 GitHub 仓库/分支 commit 变化来源，不扩展邮件、日历、Webhook、任意 URL 或新的网络权限。

1. **E1 来源与事件：** 复用已存在的观察事实/游标，统一有来源标识的事件入口和去重；元数据在现有 SQLite 增量维护，不复制任意业务正文，不另建事件框架。
2. **E2 订阅与归属：** 显式创建、查询、停用主题/Goal订阅；来源和目标必须当前可见，订阅只决定事件送给谁，不产生执行授权。
3. **E3 原执行链与 Web：** 有已批准且仍有效的原 Policy/Grant 才交原执行入口；未授权事件只观察/显示。若当前 Web 尚无对应授权入口，先具体说明需要增加什么权限，再交用户决定；不能拼接 Console/飞书身份来绕过限制。
4. **E4 阶段验收：** 重复事件、轮询、重启、停用订阅、失效政策、错误目标均不重复或越权执行；后续事件继续找到原工作主题/Goal。模拟网络和临时数据库验证，不做真实 GitHub 轮询或收费模型试验。

### 阶段 4：关联回忆

从现有 WorkThread 关系、WorkJob/Run、Goal执行和事件来源组织可追溯结果，复用既有读取与归属校验；不新增向量库或长期记忆事实源。

1. **R1 定位：** 当前选择/明确对象优先，“上次那个工作”等自然引用通过有界候选定位；多候选先澄清，不仅凭相似度擅选。
2. **R2 结果与来源：** 按主题取可见关联对象和原始结果，给出对象/Run/事件来源；删除或不可见对象明确不可用，不从关系取得额外权限。
3. **R3 Web 接线：** 复用主题、聊天和结果视图展示回忆结果与跳转；低信任结果不当指令，不赋予 Task/Goal/文件审批权限。仅在确有需要且满足既有 Memory 访问边界时复用检索，不自动保存。
4. **R4 总体验收：** 两主题隔离、正确引用/歧义、来源缺失、对象状态变化、事件到结果的追溯、功能关闭兼容；全量工程测试及桌面/窄屏离线闭环，单列未执行的真实模型/手机/长跑验证。
