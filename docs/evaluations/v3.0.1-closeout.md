## 根因与修复边界

原请求45将“计划一项：阅读一段TypeScript入门说明”生成三个正式Step：确认计划与首段主题、阅读说明、提炼要点形成记录。摘要仍称“单一计划项”。这既混淆安排与Step，也把宿主已负责的计划批准变成了额外Step，并自行扩展复述产物。旧结果Schema与四表事务只能证明结构合法，不能证明自然语言数量和范围遵从。

“一项安排”不能直接证明“一个正式Step”；一个Step也可在说明中包含多个内部动作。因此保留旧报告的原一步草稿预期未达，不反过来修改旧失败；新规则明确区分三种口径：

| 用户口径 | 宿主处理 |
| --- | --- |
| 正式计划最多两步、不超过2个Step、恰好两步、至少两步、两至三步等可核对数量 | 从原始Goal原话提取有界上下界，计算完整正式Step总数，包含已完成Step；草稿创建/修改和审批均校验。越界或冲突整体拒绝，不裁剪、不提交半个Checkpoint、不自动补模型请求。 |
| 计划一项/只安排一项阅读内容，未指明正式Step数 | 不强转为一个Step。多Step草稿原样保留并突出数量口径待确认；短“确认”或普通批准不能通过。用户阅读后明确“批准计划，允许将1项安排拆成3步”才接受该拆解，仍不增加执行授权。 |
| 安排数量与正式Step边界均明确，例如“一项阅读，正式计划最多三步” | 校验正式Step边界，不要求二者数值相等。 |
| 一个任务、一道题、每次只执行一步、Step说明里的内部子步骤、引用/假设或子计划数量 | 不自动作为整个正式Plan的Step总数。 |

模型只收到数量口径提示，不能提供宿主数量字段或修改原话。数量校验位于同一SQLite事务；明确边界失败回滚，Runner公开具体原因后保守阻塞，旧有效Checkpoint不变。较早版本已经保存的待批草稿在审批口也不能绕过。原始Goal是不可变目标：这些边界持续约束后续版本，普通批准/增补不能悄悄提高原边界；需要改变目标本身时新建Goal，本轮不引入目标原文修改机制。

原“暂停那个学习计划”修复继续要求唯一、完整、成功投递、未过期且版本一致的视图；具名筛选与指代取交集。新增回归发现原修复对“那个……还是这个……”可能仍按唯一视图暂停，因此增加有界歧义拦截：多个指向、二选一/另一个/其他目标或同时暂停取消时只澄清。没有从模型last标签推导权限，也没有扩大取消、引用、跨渠道或旧清单权限。

## 仍然不能证明的事项

- 数量规则是对原始Goal的限定语法校验，不是通用自然语言理解器；复杂省略、其他量词、隐含范围可能未识别。追加反馈里的新数量目前仍由模型理解，不升级成新的持久边界；需要改变原目标数量边界时新建Goal。逐项内容是否仍属原安排、是否扩展了复述/测试等产物需模型和用户核对，宿主不声称完整语义证明。
- 拆解确认仅接受可核对的数量与完整独立子句；复杂措辞会继续澄清，不借模型参数放行。不会自动提高原Goal数量边界。
- 真实模型是否遵从新提示、原自然暂停及新增歧义拦截、取消/目标选择尚未收费复验；手机/飞书本轮仍未操作。Batch5旧失败不因离线成功变绿。
- 通知仍无Outbox，保留原投递故障边界；本轮没有增加可靠消息平台、自动修复或自主重试。
