实现仍是约150行的纯检索模块，不引入 NER、向量库或额外模型。`retrieve()` 分别返回 Top5 `records`、所有排序后相关 `relatedIds`、逐条 `evidenceById`（主体/字段/原文引句）及 Top5 内 `supportIds`。原文引句只用于本轮证明，不是新的事实源或权限。

状态的实际含义：

- `none`：没有满足当前约束且有词法相关性的候选。
- `insufficient`：已识别主体/所问字段且有相关资料，但对应子句没有所问事实。
- `uncertain`：字段未知、主体归属不明、存在多主体歧义，或证据被截断，无法可靠判定。
- `supported`：限定规则在同一主体子句中找到了所问字段证据；多主体比较要求各主体分别覆盖。仍需生成模型核对正文和限定条件，**不是通用语义证明**。

日期匹配、排除约束、字段不能被改写覆盖、版本与删除、预算和权限可以由宿主确定性验证。任意指代、任意属性关系、复杂否定、任意中英文表达和最终措辞是否忠于证据，仍不能由本次有界规则保证。无法识别时保守标记，而不是把任意金额/语言词认定为答案。

## Context 与候选排序的关系

1. Top5 是召回排序结果，不等于5个答案。类型/字段证据可以加分，多主体比较先保证各主体的候选有代表。
2. Context 先取 Top5 内有主体/字段证明的项，再取其余 Top5，最后取本轮工具选中且满足原始约束的当前记录。不是用 `supportIds` 做独占过滤，也不增加容量。
3. 每次构造重新读取当前 Markdown、Hash 和索引；工具选择只保存 ID，不能使旧正文/旧版本复活。仍通过原 Pi 公开 `context` Hook 临时投影，后台保持独立只读 Session。
4. 头部明确问题主体、字段、证据边界；每项保留 ID/kind/key/version/source 与证据标签。只有实际装入正文的引句才能算可见证明；若引句被截断，逐条及整体 `supported` 会降级。
5. `memory_context` 事件分别记录候选、支持项、实际注入 ID/version、检索/实际证据状态和字节占用，不记录引句/正文。Context 仍全部低信任，无法授予任何写权限。

保留参考候选能让生成阶段看到“资料相关但没有答案”，也会增加非答案片段。下面同时报告命中与严格预期 key 比例，避免用更大的 Context 隐藏排序问题。
